Speeding Up Paging: TLB & EMAT

Tanenbaum Section 3.3.3 (Fig. 3-12): The real-world necessity of associative caching, array locality, and Effective Memory Access Time.

Why Is the TLB Essential? The Array Bottleneck

To understand why a TLB is critical to modern computer architecture, consider what happens during everyday programming routines—such as summing an array of 1,024 integers (4,096 bytes, exactly 1 standard 4 KB page):

int total = 0; for (int i = 0; i < 1024; i++) { total += data[i]; // All 1,024 integers reside on the same 4 KB virtual page! }

Assume a typical system: CPU execution core access takes 1 ns, but an off-chip DRAM lookup takes 50 ns. On a 64-bit architecture with 4-level paging (PML4 → PDPT → PD → PT):

  • Architecture WITHOUT a TLB: For every single element in the loop, the CPU must resolve the virtual address of data[i]. It reads Level 4 (50 ns), Level 3 (50 ns), Level 2 (50 ns), and Level 1 (50 ns), then finally reads data[i] itself (50 ns).
    Cost per loop iteration: 250 ns.
    Total cost for 1,024 integers: 1,024 × 250 ns = 256,000 ns (0.256 ms). The CPU spends 80% of its execution time stalled on redundant pointer reads for the exact same page!
  • Architecture WITH a TLB:
    Iteration 0: Compulsory TLB Miss → Walk 4 levels of DRAM (200 ns) → Cache translation in TLB → Fetch data (50 ns) = 250 ns.
    Iterations 1 to 1,023: TLB Hit! The associative register matches the Virtual Page Number in < 0.5 ns. The 4-level DRAM walk is bypassed completely! Fetch data from L1 cache (~1 ns) = ~1.5 ns per element.
    Total cost for 1,024 integers: 250 ns + (1,023 × 1.5 ns) ≈ 1,784 ns (0.00178 ms).
Speedup = 256,000 ns / 1,784 ns ≈ 143x Faster!
Without a TLB, modern 3.0 GHz processors would spend nearly all their cycles waiting on memory bus lookups. The TLB cuts translation overhead to zero for >98% of instructions.
