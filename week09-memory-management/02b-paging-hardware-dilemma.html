Paging in Action & The Implementation Dilemma

Tanenbaum Sections 3.3.2 & 3.3.3: How linear page tables work in memory, and the conflicting hardware constraints that require a TLB.

1. The Linear Page Table as an Array

In the previous lesson, we dissected the individual Page Table Entry (PTE) and its control bits (Present, Protection, Modified, Referenced). But where do these entries actually live, and how does the CPU look them up?

Conceptually, the simplest page table is a linear indexed array. Every process has its own page table. When the CPU executes an instruction referencing virtual address 0x00004080 with 4 KB pages (212 = 4,096 bytes):

Virtual Address = [ Virtual Page Number (VPN) : 20 bits ] [ In-Page Offset : 12 bits ]
VPN = 0x00004080 >> 12 = 4
Offset = 0x00004080 & 0xFFF = 0x080

The hardware MMU simply indexes into the array: PTE = PageTable[VPN]. If PTE.present == 1, the MMU takes the Page Frame Number (PFN) from that slot, concatenates the original 12-bit offset, and emits the physical address onto the memory bus.

2. Tanenbaum's Two Conflicting Constraints

As Tanenbaum emphasizes at the start of Section 3.3.3, any hardware implementation of paging must confront two fundamental dilemmas:

  1. Constraint 1: The mapping must be blazingly fast. A typical instruction executes in under 1 ns, and memory is referenced multiple times per instruction (once to fetch the instruction, and often 1–2 times to fetch operands). If translation adds even 10 ns, the entire computer slows down by an order of magnitude.
  2. Constraint 2: If the virtual address space is large, the page table is gigantic. A 32-bit address space with 4 KB pages has 232 / 212 = 220 (1,048,576) pages. At 4 bytes per entry, each process needs a 4 MB page table. In a system running 100 processes, 400 MB of RAM is consumed just for bookkeeping tables! On 64-bit architectures with 252 pages, a linear table is physically impossible.

3. The Extreme Implementation Choices

Before arriving at the modern solution, operating systems historically evaluated two extremes:

Extreme 1: Pure Hardware Registers

Store the entire page table inside fast CPU registers inside the MMU.

Pros: Extremely fast. Zero DRAM lookup overhead (< 1 ns).
Cons: Storing 1,000,000 registers on-chip is cost-prohibitive. Furthermore, on every context switch, the OS must reload all 1,000,000 registers, crippling multitasking.
Extreme 2: Pure Memory-Resident Table

Keep the table entirely in off-chip DRAM. The CPU holds only 1 register: the Page Table Base Register (CR3).

Pros: Cheap. Context switching is instant: simply write 1 register (pointer to the new process table).
Cons: Doubles (or quintuples) memory access latency. Every single variable access requires a DRAM lookup before fetching the data.
The Solution: The Hybrid TLB

Keep the full table in DRAM, but equip the MMU with an on-chip associative cache (the TLB) for the ~64 hottest entries.

Result: Fast context switching (point CR3 to new table), near-zero latency for 98% of accesses (TLB hits), and bounded memory footprint!
