04. Thread Implementation & Pthreads

While the conceptual thread model establishes threads as lightweight units of execution within a shared address space, the critical engineering decision is where those threads are implemented and scheduled: purely in user space, directly within the operating system kernel, or through a hybrid combination of both.

1. User-Level Threads (ULT: Many-to-One Model)

In a pure user-level thread implementation, the operating system kernel is completely unaware of multithreading. The kernel treats the entire process as a single, traditional thread of control with a single Process Control Block (PCB).

Multithreading is managed entirely in user space by a runtime library (such as historical GNU Portable Threads or early Java "Green Threads"):

  • User-Space Thread Table: The runtime library maintains its own private Thread Control Blocks (TCBs) in user memory, tracking the Program Counter, registers, stack pointer, and state (Running, Ready, Blocked) for each thread.
  • User-Space Context Switching: When a thread yields control (e.g., via thread_yield()), the runtime library saves CPU registers into the thread's user-space TCB, selects another ready thread from its queue, and restores the new thread's registers using machine routines similar to setjmp() and longjmp().
  • Extreme Context-Switch Economy: Because the switch involves no supervisor traps, no privilege ring transitions (Ring 3 to Ring 0), and no kernel scheduler invocations, switching threads requires only a handful of CPU assembly instructions, completing in nanoseconds.

The Two Fatal Flaws of User-Level Threads

  1. The Blocking System Call Problem: If Thread 1 issues a blocking system call (such as a synchronous disk read() or network recv()), the CPU traps into kernel mode. Because the kernel sees only a single monolithic process, the entire process is transitioned to the Blocked state. Even though Threads 2 and 3 in user space are fully ready to perform calculations, the kernel will not schedule the process until the I/O finishes.
  2. Inability to Exploit Multicore Hardware: Because the kernel allocates only one physical execution slot to the process, all user-level threads must time-share that single kernel thread. Even on a 64-core processor, a user-level multithreaded application can saturate at most one physical CPU core.

2. Kernel-Level Threads (KLT: One-to-One Model)

In a kernel-level thread model, the operating system kernel directly recognizes, creates, and manages every thread of execution. Every user-level thread is mapped one-to-one to an independent kernel scheduling entity.

  • Kernel TCB Management: The kernel maintains both the process table and an official kernel thread table. Scheduling, prioritization, and preemption are handled directly by the kernel's CPU scheduler.
  • True Hardware Parallelism: If a process spawns four threads on a quad-core processor, the kernel scheduler assigns each thread to a distinct physical core, executing all four threads simultaneously in silicon.
  • Independent Blocking: If Thread 1 blocks waiting on disk I/O, the kernel suspends only Thread 1. The kernel scheduler immediately switches the CPU core to Thread 2 or Thread 3 of the same process, preventing the application from freezing.
  • The Context-Switch Tax: Creating a thread or switching between threads requires a supervisor system call trap (entering Ring 0), saving kernel stack states, and invoking the kernel dispatcher. While substantially cheaper than a full process context switch (because virtual memory page tables remain unchanged), it is orders of magnitude slower than a user-space thread switch.

Why The System Does This

User-level threads allow applications to implement custom scheduling policies without kernel support, achieving near-zero overhead switches when operations remain non-blocking.

3. Hybrid Threading Models (M:N & Two-Level)

To combine the nanosecond context-switch speed of user-level threads with the multicore parallelism and non-blocking robustness of kernel-level threads, computer scientists developed the M:N hybrid model (historically implemented in Solaris Light-Weight Processes and modern language runtimes such as Go's goroutine scheduler):

  • $M$ user-level application threads are dynamically multiplexed over a smaller pool of $N$ kernel-level worker threads.
  • If a user thread executes compute-bound code, it switches in user space without entering the kernel.
  • If a user thread issues a blocking I/O system call, the kernel blocks only that specific underlying kernel worker thread. The user-space runtime immediately migrates the remaining runnable user threads to other surviving kernel worker threads.
  • Scheduler Activations & Upcalls: To coordinate state between user space and kernel space without polling, the kernel uses upcalls—the kernel signals the user runtime when a thread blocks or unblocks, allowing the user scheduler to rebalance work dynamically.

4. The POSIX Threads (Pthreads) Standard

To ensure source-code portability across diverse UNIX and POSIX-compliant operating systems, the IEEE standardized the POSIX 1003.1c standard, commonly known as Pthreads. Pthreads defines an explicit C language interface for thread creation, lifecycle synchronization, and mutual exclusion.

Core Pthreads Lifecycle API

Function Prototype Operational Description
int pthread_create(pthread_t *thread, const pthread_attr_t *attr, void *(*start_routine)(void *), void *arg); Spawns a new thread executing start_routine(arg) with configurable stack and scheduling attributes.
int pthread_join(pthread_t thread, void **retval); Blocks calling thread until the target thread terminates, reaping its return pointer and resources (similar to waitpid).
int pthread_detach(pthread_t thread); Marks thread as detached; its storage is automatically reclaimed by the runtime immediately upon termination without requiring a join.
void pthread_exit(void *retval); Terminates the calling thread voluntarily, passing retval to any waiting pthread_join() invocation.

Concrete Pthreads Implementation Example

The following C program demonstrates thread creation, argument passing via heap structures, thread synchronization via joining, and mutual exclusion locking: 

#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
long shared_counter = 0;

void *worker_routine(void *arg) {
    long iterations = *(long *)arg;
    for (long i = 0; i < iterations; i++) {
        pthread_mutex_lock(&lock);
        shared_counter++;  /* Critical section guarded by mutex */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    long counts = 1000000;

    pthread_create(&t1, NULL, worker_routine, &counts);
    pthread_create(&t2, NULL, worker_routine, &counts);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("Final Counter: %ld\n", shared_counter);
    return 0;
}

5. Linux Native POSIX Thread Library (NPTL) & clone(2)

Linux implements Pthreads using the Native POSIX Thread Library (NPTL). Underneath the POSIX wrapper, the Linux kernel does not have a separate data structure for threads versus processes. Instead, every execution context is represented uniformly by a struct task_struct.

The pthread_create() library function invokes the versatile Linux clone(2) system call, supplying explicit sharing flags that govern resource inheritance: 

int tid = clone(worker_func, child_stack_top,
                CLONE_VM | CLONE_FS | CLONE_FILES |
                CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM,
                arg);
  • CLONE_VM: The new task shares the exact same virtual memory page tables as the caller, pointing to the same Memory Descriptor (mm_struct).
  • CLONE_FILES: The new task shares the file descriptor table; an open() or close() in one thread is immediately visible to all other threads.
  • CLONE_FS: The new task shares filesystem attributes (working directory, root directory, umask).
  • CLONE_SIGHAND: The new task shares signal handlers and dispositions.
  • CLONE_THREAD: The new task is placed in the same thread group as the caller, assigning it the same visible Process ID (PID) while retaining its own unique Thread ID (TID).
