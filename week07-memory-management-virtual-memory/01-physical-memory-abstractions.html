Physical Address Spaces & Monoprogramming

Trace the historical evolution of computer memory management from bare-metal monoprogramming without abstractions to hardware-assisted relocation and bounds protection using base and limit registers.

1. Bare-Metal Execution & The Monoprogramming Era

In the earliest digital computers—ranging from the vacuum-tube mainframes of the 1950s (such as the IBM 704 and 7094) to early personal computers running CP/M and MS-DOS—operating systems provided no memory abstraction whatsoever. Every program accessed raw physical memory directly.

When a compiler emitted an instruction such as: 

MOV [0x1200], AX    ; Direct physical memory write
JMP 0x4000          ; Direct jump to physical memory address 0x4000

The value 0x1200 or 0x4000 was placed directly onto the processor's hardware address bus pins. The hardware RAM circuit responded directly to these physical voltage lines.

Historical Physical Memory Layouts

Under a monoprogrammed operating system, only a single user program runs at any given moment. Memory was divided into at most two contiguous partitions: the operating system routines and the user program:

Model A: OS in ROM at Bottom

Common in embedded controllers and early palmtop computers. The operating system resides in Read-Only Memory at low physical memory ($0 \times 0000$), while user RAM starts immediately above.

Model B: OS in RAM at Top

The canonical MS-DOS model on the IBM PC. User applications start at low physical memory (offset 0x0100 for .COM executables), while the operating system and device drivers sit at the top of conventional 640 KB memory.

Model C: OS in Low RAM with ROM Drivers

Early minicomputer systems (PDP-11). Device drivers and BIOS reside in high ROM addresses, the kernel resides in low RAM, and user space occupies the middle band.

The Fundamental Failure of Monoprogramming: Because user code could write to any physical address, a stray pointer or rogue instruction could overwrite kernel interrupt vectors or device tables, instantly freezing the machine. Furthermore, CPU utilization was dismal: whenever the running application waited for punch card readers, magnetic tape, or disk I/O, the processor sat completely idle.

2. Multiprogramming via Static Relocation & Linkage

To maximize CPU efficiency, operating systems needed to keep multiple programs resident in physical memory simultaneously. If Process $A$ blocked for I/O, the CPU could switch immediately to Process $B$.

However, if multiple programs are loaded concurrently, they cannot all occupy physical address 0x0000. Consider two independently compiled binaries that both execute JMP 0x1000. If Process $B$ is loaded at physical address 0x8000, its internal jump instruction must somehow jump to 0x9000 instead.

Static Software Relocation

Early systems solved this via static relocation during program loading (the IBM System/360 approach):

  • The compiler produces relocatable machine code accompanied by a relocation dictionary identifying every absolute address reference.
  • When the OS loader decides to load Process $B$ starting at physical address $L = \text{0x8000}$, the loader physically modifies the binary in RAM, adding offset $L$ to every jump and memory reference.

Limitations of Static Relocation:

  1. High Load Latency: Loading an application requires parsing and rewriting thousands of memory words.
  2. Immobility: Once loaded, a process cannot be easily swapped out to disk and returned to a different physical memory address without re-patching every pointer.
  3. Zero Protection: Process $A$ can still forge an address pointing into Process $B$'s memory space and corrupt its data.

3. Dynamic Hardware Relocation: Base & Limit Registers

The breakthrough that enabled true, secure multiprogramming was dynamic hardware relocation, pioneered on computers such as the CDC 6600 and the GE-645.

Instead of modifying instructions at load time, the CPU incorporates two dedicated hardware registers into its execution pipeline: the Base Register and the Limit Register (also called the relocation and protection registers).

Hardware Relocation Invariant:

$$ \text{Physical Address} = \text{Logical (Virtual) Address} + \text{Base} $$ $$ \text{Hardware Bounds Check: } 0 \le \text{Logical Address} < \text{Limit} $$

Under this architecture, every program is compiled as if it owns an isolated address space starting at virtual address $0$. The CPU pipeline transparently translates every memory reference in real time:

  1. The CPU hardware compares the logical address against the Limit Register.
  2. If the logical address is $\ge \text{Limit}$, the CPU raises a hardware exception (a segmentation fault or memory protection trap), terminating the process.
  3. If the bounds check passes, the Base Register is added to the logical address on the hardware bus to generate the physical address for RAM.

4. Swapping vs. Overlays

In systems where physical RAM capacity is insufficient to hold all active applications simultaneously, operating systems resorted to two primary techniques:

Memory Overlays (Application-Managed)

In the 1960s and 1970s, programs were frequently larger than total core memory. Software engineers manually partitioned programs into a root module and mutually exclusive overlays:

  • The root module remained permanently in memory.
  • When Phase 1 of a compiler finished parsing, the overlay manager loaded Phase 2 (code generation) into the exact same memory partition previously occupied by Phase 1.

Defect: Overlays placed an immense intellectual burden on programmers, who had to manually construct complex overlay trees ($V = V_0 + \max(V_1, V_2)$) without kernel automation.

Process Swapping (Kernel-Managed)

Swapping automated multi-process concurrency by moving entire process memory images between RAM and a dedicated backing store (disk swap partition):

  • When a process blocks on user input or runs out of execution quantum, the OS swaps its entire contiguous address space out to disk.
  • Another ready process is swapped from disk into RAM.
  • Base Register Benefit: Because base and limit registers relocate addresses dynamically at runtime, when a process is swapped back into RAM, it does not need to return to its original physical location. The OS simply loads it into any available contiguous free slot and updates its Base Register.

5. Memory Fragmentation: Internal vs. External

In any dynamic storage allocation system, memory fragmentation is the inevitable systemic inefficiency that arises as processes are allocated, expanded, and released over time. Understanding the exact mechanical distinction between Internal Fragmentation and External Fragmentation is fundamental to OS memory architecture.

1. Internal Fragmentation: Allocation Quantum Slack

Internal fragmentation occurs when memory is assigned in fixed-size allocation quanta or granularity blocks (such as fixed partition slots, power-of-two blocks in buddy allocators, or 4 KB paging frames). When an application's requested memory footprint does not align perfectly with the hardware or allocator's unit size, the system must round up to the nearest whole block.

The Intuitive Analogy: Fixed Egg Cartons

Imagine eggs are sold strictly in fixed cartons of a dozen ($S = 12$). If a recipe requires 14 eggs ($R = 14$), the supermarket will not sell you 1.16 cartons. You are forced to purchase 2 whole cartons (24 eggs). The 10 empty egg slots sitting in your fridge represent internal slack: space you paid for and occupy, but cannot use or share with anyone else.

Mathematical Definition of Internal Slack:

Let $S$ be the fixed hardware block size, and let $R$ be the requested payload size ($R > 0$). The allocated memory $A$ and internal slack $W_{\text{internal}}$ are given by: $$ A = \lceil R / S \rceil \times S $$ $$ W_{\text{internal}} = A - R $$

Note: The ceiling brackets $\lceil x \rceil$ denote the ceiling function, which always rounds up to the next integer (e.g., $\lceil 1.22 \rceil = 2$).

Step-by-Step Numeric Walkthrough

Consider a standard operating system allocating memory in standard 4 KB (4096-byte) pages:

  1. Program Request ($R$): Your application requests $5000\text{ bytes}$ ($R = 5000$, $S = 4096$).
  2. Divide by Block Size: $R / S = 5000 / 4096 \approx 1.2207\text{ blocks}$.
  3. Apply Ceiling Rounding ($\lceil \dots \rceil$): Because the hardware MMU cannot allocate fractions of a page, the OS rounds up to $\lceil 1.2207 \rceil = 2\text{ full blocks}$.
  4. Compute Total Memory Allocated ($A$): $A = 2 \times 4096 = 8192\text{ bytes}$.
  5. Determine Internal Slack ($W_{\text{internal}}$): $$ W_{\text{internal}} = A - R = 8192 - 5000 = 3192\text{ bytes} $$

These $3192\text{ bytes}$ are trapped inside the boundary of the second page allocated to your process. Because that physical page belongs exclusively to your process, the kernel cannot lend those remaining 3192 bytes to any other program.

Statistical Expectation: The Half-Block Rule

What is the average waste across thousands of processes? If program memory requests are uniformly distributed, the wasted space in the final page ranges from $1\text{ byte}$ (if requesting 4095 bytes) to $4095\text{ bytes}$ (if requesting 4097 bytes). Averaged across all random allocations, the expected waste per segment is exactly half an allocation block:

$$ \mathbb{E}[W_{\text{internal}}] = \frac{0 + S}{2} = \frac{S}{2} $$

In a system with $N$ active allocations and a 4 KB allocation granularity ($S = 4096$), the kernel wastes approximately $N \times 2048$ bytes of physical RAM simply through internal block rounding.

2. External Fragmentation: Checkerboard Hole Formation

External fragmentation emerges in variable-sized contiguous allocation schemes (such as dynamic partitioning with Base and Limit registers). As processes of varying sizes enter and terminate at arbitrary times, free contiguous memory is fragmented into a scattered collection of small, non-contiguous "holes."

A system suffers from external fragmentation when the sum total of all free memory holes is sufficient to satisfy a process allocation request, but no single contiguous hole is large enough to hold the process.

External Fragmentation Condition:

$$ \sum_{k=1}^{M} \text{Size}(\text{Hole}_k) \ge \text{RequestedSize} \quad \land \quad \max_{1 \le k \le M} \big(\text{Size}(\text{Hole}_k)\big) < \text{RequestedSize} $$
Knuth's 50% Rule of Allocation

In The Art of Computer Programming (Vol. 1), Donald Knuth proved a fundamental statistical theorem governing contiguous dynamic storage allocation under steady-state conditions:

Knuth's 50% Rule:

$$ M \approx \frac{1}{2} N $$

In steady state, if $N$ blocks are actively allocated, the number of isolated free holes $M$ tends asymptotically toward $N / 2$, regardless of whether First-Fit or Best-Fit allocation is used.

Consequence: If each hole is approximately the same average size as an allocated block, approximately one-third of all physical memory is rendered unusable due to external fragmentation: $$ \text{Fraction of Memory in Holes} \approx \frac{M}{N + M} = \frac{0.5 N}{N + 0.5 N} = \frac{0.5}{1.5} \approx 33.3\% $$

3. Resolving External Fragmentation: Memory Compaction

To reclaim checkerboarded free memory in a contiguous system, the operating system must execute Memory Compaction (relocation defragmentation). The kernel shifts all active processes toward one end of physical memory (usually toward address $0$), coalescing all isolated holes into a single contiguous pool.

Compaction Mechanics & Algorithms
  • Sliding Compaction: Active segments are slid downward toward low memory while preserving their original relative ordering. This minimizes displacement distance and preserves data cache spatial locality.
  • Two-Finger Compaction (LISP-style): Uses two pointers moving toward each other: a free-space scanner starting at memory zero and a process scanner starting at high memory. Processes from the top are moved into free slots at the bottom. While faster, it scrambles process ordering.
The Cost of Compaction

Compaction imposes severe architectural performance penalties:

  1. Bus Saturation & Latency: Compacting 16 GB of active RAM across memory channels at 25 GB/s stalls the system for over 600 milliseconds—an unacceptable latency spike for interactive and real-time operating systems.
  2. Hardware Prerequisite: Compaction is impossible under static relocation. It requires hardware-assisted dynamic relocation (Base and Limit registers), because every moved process must have its Base Register updated to reflect its new physical offset.
  3. Direct Memory Access (DMA) Lockout: If a network card or disk controller is currently executing a DMA transfer into a process's buffer, that process cannot be moved until the hardware I/O finishes, locking memory in place.

4. Summary Comparison

Attribute Internal Fragmentation External Fragmentation
Location of Wasted Space Inside the allocated partition or page boundary. Between distinct allocated partitions (holes in RAM).
Root Cause Fixed-size allocation granularity (quanta rounding). Variable-sized allocations combined with dynamic allocation/freeing.
Typical Occurrences Paging systems (4 KB pages), Buddy allocators. Base/Limit dynamic partitioning, unpaged heap managers.
Architectural Solution Smaller allocation quanta (e.g., fine-grained slab allocators). Paging: Decouple contiguous virtual space from physical frames.
