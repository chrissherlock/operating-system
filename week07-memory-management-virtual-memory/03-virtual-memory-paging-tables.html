Module 03 • COSC240

Virtual Memory & Paging Architectures

Examine the hardware and software architecture of virtual memory: address decomposition, Memory Management Unit (MMU) operation, Page Table Entry bitfields, and multi-level hierarchical paging structures.

1. Decoupling Virtual & Physical Memory

The fundamental limitation of Base and Limit dynamic relocation (Module 01) is that each process must still occupy a strictly contiguous block of physical memory. If an application requires 16 MB of RAM, and available memory is fragmented into four separate 4 MB holes, the program cannot run without expensive compaction.

Pioneered in 1962 on the University of Manchester Atlas computer, Virtual Memory via Paging completely breaks the contiguous allocation constraint:

  • Virtual Address Space (Pages): The program's logical memory is divided into fixed-size contiguous chunks called Pages (typically 4 KB).
  • Physical Memory (Frames): Physical RAM is partitioned into identical fixed-size blocks called Page Frames.
  • Arbitrary Mapping: Any virtual page of a process can be placed in any physical frame anywhere in RAM, or held temporarily on disk backing store.

To the executing CPU core, the process appears to inhabit a massive, unbroken, contiguous array of linear addresses ($0 \dots 2^{64}-1$). In reality, the physical frames backing those pages are scattered arbitrarily throughout physical RAM. External fragmentation is completely eliminated.

2. The Mathematical Virtual Address Split

When the CPU emits a virtual memory address $VA$, the hardware Memory Management Unit (MMU) automatically splits the binary address into two distinct components:

Virtual Address (VA) = [ Page Number (p) | Offset (d) ]

Let $S = 2^n$ be the page size in bytes. For an $m$-bit virtual address space:

  • The lower $n$ bits constitute the Page Offset ($d$). The offset designates the exact byte location within the page. Because pages and frames are identical in size, the offset is transferred directly to the physical address without modification.
  • The upper $m - n$ bits constitute the Virtual Page Number ($p$). The page number is used as an index into the process's Page Table to discover which physical frame holds that page.
Bitwise Address Translation Formulas:

$$ p = \lfloor VA / 2^n \rfloor = VA \gg n $$ $$ d = VA \bmod 2^n = VA \ \& \ (2^n - 1) $$ $$ \text{Physical Address (PA)} = (f \times 2^n) + d = (f \ll n) \mid d $$

Where $f = \text{PageTable}[p].\text{FrameNumber}$ is the physical frame retrieved from the Page Table.

Concrete 32-bit Architecture Example

Consider a 32-bit system with standard 4 KB ($2^{12}\text{ bytes}$) pages:

  • Page size $S = 4096 \implies n = 12\text{ bits}$ for the Offset.
  • Virtual address width $m = 32 \implies 32 - 12 = 20\text{ bits}$ for the Virtual Page Number ($p$).
  • Virtual space accommodates $2^{20} = 1{,}048{,}576$ pages.

If the CPU references virtual address 0x0000840C: 

Virtual Address:  0x0000840C
Binary:           0000 0000 0000 0000 1000 | 0100 0000 1100
                  \______________________/   \____________/
                   Page Number p = 8 (0x8)     Offset d = 0x40C (1036)

The MMU looks up index $8$ in the Page Table. If entry $8$ contains Frame Number $f = 2$ (0x00002), the Physical Address is formed by concatenating $f$ and $d$: $$ \text{PA} = (0\text{x}00002 \ll 12) \mid 0\text{x}40C = 0\text{x}0000240C $$

Bit Field Name Hardware Function & Purpose
Present (P / Valid) Bit 0 1 if page is resident in physical RAM. 0 if page is unmapped or on disk; accessing triggers an immediate Page Fault.
Read/Write (R/W) Bit 1 0 = Read-Only (attempting to write triggers a protection fault). 1 = Read-Write. Used for code segment protection.
User/Supervisor (U/S) Bit 2 0 = Kernel mode only (Ring 0). 1 = User space accessible (Ring 3). Prevents user code from touching kernel memory.
Accessed (A / Ref) Bit 5 Set to 1 by the hardware MMU on any read or write. Inspected by page replacement algorithms (such as Clock or LRU aging).
Dirty (D / Modified) Bit 6 Set to 1 by the hardware MMU whenever a write occurs. When evicting the page, the OS knows it must write it back to disk.
Page Frame Number Bits 31–12 The upper physical address bits representing the physical RAM frame holding the page data.

4. Multi-Level Hierarchical Page Tables

In a simple linear page table design, the entire page table must reside continuously in physical RAM. On a 32-bit architecture with 4 KB pages: $$ 2^{20} \text{ entries} \times 4\text{ bytes per PTE} = 4\text{ MB per process} $$ If the OS runs 100 processes, 400 MB of physical RAM is consumed solely by page tables.

On a 64-bit architecture, a flat linear page table is physically impossible: $$ 2^{52} \text{ pages} \times 8\text{ bytes per PTE} \approx 33{,}554{,}432\text{ GB per process!} $$

The Hierarchical Solution

Real-world process address spaces are heavily sparse: an application typically uses a small code region at low memory, a small heap above it, and a small stack growing down from high memory. Gigabytes of address space in between are completely unmapped.

Multi-Level Page Tables solve the scaling dilemma by paging the page table itself:

  • Level 1 (Top Level / Page Directory): Contains pointers to Level 2 page tables.
  • Level 2: Contains pointers to actual physical page frames.
  • Sparsity Benefit: If an entire region of virtual memory is unmapped, its top-level entry is marked Present = 0. The underlying Level 2 page tables never need to be allocated in physical RAM.
x86-64 4-Level Paging Architecture:

x86-64 architectures implement 48-bit canonical virtual addressing using 4 hierarchical levels with 9 bits each, plus a 12-bit offset ($9 + 9 + 9 + 9 + 12 = 48\text{ bits}$): $$ VA = [ \text{PML4 (9b)} \mid \text{PDPT (9b)} \mid \text{PD (9b)} \mid \text{PT (9b)} \mid \text{Offset (12b)} ] $$

CR3 register → PML4 → Page Directory Pointer Table → Page Directory → Page Table → Physical Frame.

The Latency Penalty: While multi-level page tables solve the memory footprint crisis, translating a single virtual address in x86-64 requires four sequential physical memory reads before accessing the actual data! To avoid a $400\%$ memory bus slowdown, hardware incorporates a high-speed cache: the Translation Lookaside Buffer (TLB), explored in Module 04.
