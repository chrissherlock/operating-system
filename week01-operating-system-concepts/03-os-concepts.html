03. Operating System Concepts

At the heart of every computer system lies a collection of powerful architectural abstractions designed to turn raw hardware into a programmable, secure, and intuitive environment. Drawing from Tanenbaum's foundational taxonomy, this module examines the core conceptual pillars that define modern operating systems.

1. The Process Abstraction

At the foundation of operating system design is the process: an abstraction representing an active program in execution. While a program is a lifeless, passive collection of machine instructions and static data stored on non-volatile media (such as an ELF binary or Windows PE file on an NVMe SSD), a process is a dynamic, living computational entity with an active execution context managed by the kernel.

Process vs. Program: The Core Distinction

A single program can correspond to multiple distinct processes running concurrently. For example, if two users launch separate instances of the text editor nano, or if a user opens three independent terminal shells, each instance constitutes a separate process. Although both instances share the exact same underlying machine code in memory, each maintains completely isolated memory registers, dynamic heap buffers, execution state flags, and private call stacks.

Anatomy of a Process in Memory

When an operating system loads a binary executable into physical RAM to execute, it constructs a private virtual address space organized into standardized logical segments:

  • Text Segment (Code): The read-only region containing raw machine instructions executed by the CPU. Marking this region read-only prevents self-modifying code vulnerabilities and allows multiple concurrent instances of the same binary to share physical code pages in memory.
  • Data Segment (Initialized): Stores global and static variables explicitly initialized by the programmer before execution (e.g., int max_retries = 5;).
  • BSS Segment (Uninitialized): Block Started by Symbol; holds uninitialized global and static variables. Rather than bloating binary disk images with zeroes, the kernel simply records the size of the BSS section and zeroes out physical pages on demand upon allocation.
  • Heap: A dynamic memory pool managed at runtime by allocators (such as malloc() or new). The heap grows upward from lower virtual memory addresses toward higher addresses as dynamic allocations expand.
  • Stack: A Last-In, First-Out (LIFO) scratchpad region storing active execution frames. Each stack frame houses function arguments, return addresses, saved CPU registers, and local automatic variables. In typical x86 and ARM architectures, the stack originates near the top of the virtual address space and grows downward toward the heap.

The Process Control Block (PCB): Cross-Platform Realities

Because CPU cores can execute only one sequence of instructions at any given instant, the operating system kernel maintains a centralized control structure—the Process Control Block (PCB)—to manage identity, ownership, security bounds, and hardware state for every active execution entity.

Key Elements Universal to All PCBs

Despite naming differences across kernel architectures, any production operating system maintains the following core invariants inside or associated with its process control tracking:

  • Architectural Root Anchor: A hardware-mandated pointer to the top-level page table (e.g., CR3 on x86-64, TTBR0 on ARM64) enabling the MMU to swap address spaces during context switches.
  • Execution State Tracking: Flags denoting whether the entity is active, ready to run, sleeping on a synchronization primitive, or in a zombie/terminated state awaiting cleanup.
  • Security Token & Credentials: User/group identifiers (POSIX UID/GID) or Windows Access Tokens specifying privileges, security identifiers (SIDs), and audit policies.
  • Resource Descriptors & Limits: Quotas and references to system resources, including CPU affinity masks, memory working-set limits, and tables mapping private application references to underlying kernel objects.

Process State Transitions: The Three-State Model

Throughout its lifecycle, a process transitions between three core execution states:

  1. Running: The process currently occupies a physical CPU core and its instructions are executing in hardware.
  2. Ready: The process possesses all prerequisites to execute, but is temporarily stopped waiting for the CPU scheduler to allocate a core.
  3. Blocked (Waiting): The process cannot proceed—even if a CPU core is idle—because it is waiting for an external event to finish, such as reading disk sectors, receiving network packets, or waiting on a timer.

2. Address Spaces & Virtual Memory

To prevent concurrent programs from corrupting one another's memory, operating systems introduce the address space. Each process is presented with its own private, contiguous virtual memory range. The Memory Management Unit (MMU) translates these virtual addresses into physical RAM locations on the fly, providing memory isolation, protection rings, and support for swapping.

3. Files & Hierarchical Directories: Diverse Paradigms

The file abstraction provides a persistent, named container for information that survives process termination and power outages. While contemporary developers frequently assume the Unix model—a linear, untyped byte stream anchored in a single unified directory tree—operating system history reflects fundamentally different approaches to structuring persistent storage.

File Structuring Models: Byte Streams vs. Record Datasets

Operating systems categorize the internal structure of files into three primary models:

  • Unstructured Byte Sequences (POSIX / Windows): The OS treats the file as an arbitrary sequence of 8-bit bytes. The kernel imposes no internal boundaries, record structures, or record keys; interpreting the contents is left entirely to user applications.
  • Multi-Stream & Forked Files (macOS HFS / Windows NTFS): Files can house multiple discrete data streams attached to a single directory entry. Apple's classic HFS utilized a Data Fork (raw content) and a Resource Fork (compiled icons, menus, and localization strings). Similarly, NTFS supports Alternate Data Streams (ADS), allowing metadata (such as web origin tags like Zone.Identifier) to adhere silently to a file.
  • Record-Oriented Datasets (IBM z/OS / MVS / VMS): The operating system defines and enforces internal record structures. Files are sequences of fixed-length (Fixed Blocked) or variable-length records. In Indexed Sequential Access Method (ISAM) or VSAM datasets, the OS kernel itself manages indexed key searches to fetch specific customer or account records without requiring database middleware.

Namespace Topologies: Unified Trees vs. Per-Volume Roots

How an operating system organizes and accesses multiple physical disk volumes varies dramatically:

  • Unified Virtual File System (POSIX / Unix): Every physical disk, network share, and pseudo-filesystem is spliced into a single root tree starting at / using the mount operation. Physical boundaries are completely transparent to userspace paths (e.g., /home/user/docs might reside across three distinct NVMe and NFS storage devices).
  • Drive Letters & The NT Object Manager (Windows): Exposed to users as segmented per-drive root directories (C:\, D:\). Internally, the Windows NT Object Manager maintains a unified root namespace (\GLOBAL??\C: symlinked to \Device\HarddiskVolume1), with Win32 path prefixes providing compatibility.
  • Flat Cataloged Namespaces (IBM Mainframes): Traditional z/OS does not use hierarchical directory trees for datasets. Instead, datasets use dotted qualifiers (e.g., USER1.COBOL.SOURCE(MAIN)) tracked via a centralized system catalog (Master and User Catalogs) mapping names to volume serial identifiers (VOLSERs).

4. Input/Output (I/O) Subsystems

The I/O subsystem abstracts diverse hardware peripherals—from keyboards to NVMe storage arrays—behind standardized device drivers and system calls. Kernels utilize interrupt handlers, device buffers, and asynchronous completion queues to decouple slow peripheral operations from fast CPU instruction cycles.

5. Protection & Security

Multi-user and networked operating systems enforce strict access controls to safeguard data. Mechanisms include:

  • User and Group Identifiers (UID/GID): Associates processes with specific security principals.
  • Access Control Lists (ACLs) & Permission Bits: Dictate whether read, write, or execute privileges are granted.
  • Privilege Rings: Hardware-enforced separation between unprivileged user mode and supervisor (kernel) mode.

6. The Command Interpreter (The Shell)

The shell is not part of the kernel, but it is the primary user interface for interacting with operating system services. When a user enters a command, the shell parses the input, issues fork() to create a child process, executes exec() to load the binary program, and manages input/output redirection and piping.
