03. Scheduling in Interactive Systems

Unlike batch architectures that maximize total computational throughput, desktop operating systems, mobile devices, and multi-tenant web servers operate under user scrutiny. In interactive environments, the primary metric is Response Time (Tresponse)—the delay between a user action (keystroke, tap, network packet arrival) and the visible system response.

1. Round-Robin (RR) Scheduling

Round-Robin is the oldest, simplest, and most reliable preemptive scheduling algorithm designed for time-sharing systems:

  • The scheduler maintains the Ready queue as a circular FIFO list.
  • Each ready process is granted a fixed execution slice called a time quantum (or time slice, denoted q), typically between 10 ms and 100 ms.
  • If the process blocks for I/O before q expires, it voluntarily yields the CPU.
  • If the process is still running when q expires, a hardware timer interrupt vectors execution into the kernel dispatcher. The running task is preempted and placed at the tail of the Ready list, and the next process is dispatched.

The Quantum Sizing Dilemma

The choice of time quantum length q fundamentally controls the balance between raw throughput and interactive responsiveness:

Turnaround vs. Response Trade-off in Round-Robin

While Round-Robin provides exceptional fairness and guarantees an upper bound on response time (with n processes and quantum q, no process waits longer than (n − 1) × q time units before its next slice), its average turnaround time is often substantially worse than Shortest Job First.

If three processes with burst lengths of 10 ms run under RR with q = 1 ms, all three complete nearly simultaneously around T = 28, 29, and 30 ms (average turnaround ≈ 29 ms). Under SJF, they complete at 10, 20, and 30 ms (average turnaround = 20 ms). Round-Robin deliberately sacrifices average turnaround time to ensure immediate response times for all tasks.

2. Priority Scheduling & Dynamic Aging

In production systems, processes are not created equal. A critical window manager rendering 120 FPS display frames must preempt a background virus scanner. Priority scheduling assigns each task a priority integer, and the scheduler dispatches the highest-priority runnable process first.

The Priority Inversion Dilemma

Strict priority scheduling introduces a lethal synchronization vulnerability known as Priority Inversion:

  1. Low-priority task L acquires a shared lock/mutex (e.g., sound device driver).
  2. High-priority task H arrives and attempts to acquire the mutex. Because L holds the lock, H blocks.
  3. Medium-priority task M (which does not need the lock) becomes runnable. Because Priority(M) > Priority(L), M preempts L and runs continuously.
  4. The Inversion: Task L cannot finish its critical section to release the lock because M is monopolizing the CPU. High-priority task H is indirectly starved by medium-priority task M!

Solution (Priority Inheritance Protocol, PIP): When task H blocks waiting for a lock held by L, the kernel temporarily boosts task L's priority to match H. Task L runs with high priority, completes its critical section rapidly, releases the lock, drops back to its base priority, and allows H to run immediately.

Dynamic Aging to Eliminate Starvation

To prevent low-priority background processes from starving indefinitely when a stream of high-priority interactive tasks exists, schedulers implement dynamic aging. The effective priority is calculated as: 

Peffective = Pbase + k × Twait

As a task waits in the Ready queue, its priority climbs steadily. Eventually, its effective priority surpasses active interactive tasks, guaranteeing that every process receives CPU time.

3. Multi-Level Feedback Queues (MLFQ)

Corbato's Multi-Level Feedback Queue (MLFQ) is the foundational discipline of modern general-purpose schedulers. Its objective is to solve the fundamental scheduling dilemma: how can a scheduler optimize turnaround time (like SJF) and minimize response time (like RR) without any prior knowledge of job lengths?

MLFQ learns from the past behavior of a process to predict its future behavior, establishing a hierarchy of distinct priority queues (e.g., Q0 at top priority down to Q2 at bottom priority).

The Five Fundamental MLFQ Rules

  • Rule 1: If Priority(A) > Priority(B), A runs and B does not.
  • Rule 2: If Priority(A) == Priority(B), A and B run in Round-Robin using the time quantum of that specific queue (qi).
  • Rule 3: When a new job enters the system, it is placed at the highest-priority queue (Q0).
  • Rule 4 (Allotment Accounting): Once a process consumes its total time budget Si at queue level Qi (regardless of how many times it voluntarily yielded the CPU for I/O), its priority is demoted by one level to Qi+1.
  • Rule 5 (Periodic Priority Boost): After some time period Tboost, all jobs in the system are moved to the top queue (Q0).
Why Rule 4 & Rule 5 are Critical:
Preventing Gaming of the Scheduler: Early MLFQ implementations reset a process's quantum if it voluntarily yielded for I/O before the quantum expired. Malicious or poorly designed programs exploited this by running for 99% of the quantum, issuing a trivial I/O call, yielding the CPU, and staying at top priority forever. Rule 4 tracks cumulative CPU consumption, demoting tasks once their allotment expires regardless of yielding.

Adapting to Phase Changes & Starvation: Rule 5 solves two problems: (1) it guarantees that long batch compute jobs sitting at the bottom queue cannot starve, and (2) if a compute-bound job transitions into an interactive phase (e.g., waiting for user input after completing a calculation), the priority boost gives it an opportunity to prove its new interactive behavior.

4. Proportional-Share & Lottery Scheduling

An alternative philosophical approach to priority scheduling is Proportional-Share (Fair-Share) scheduling. Instead of optimizing for response time or turnaround, the objective is to guarantee that every task receives a precise mathematical percentage of CPU execution time.

Lottery Scheduling

Developed by Waldspurger and Weihl, Lottery Scheduling uses randomness to achieve proportional fairness:

  • Processes are issued a discrete number of lottery tickets. If Process A holds 75 tickets and Process B holds 25 tickets, Process A is entitled to 75% of CPU time and Process B to 25%.
  • At each scheduling slice, the operating system picks a winning ticket at random (generating a random integer between 1 and 100). The process holding the winning ticket is granted the CPU.
  • Probabilistic Convergence: Over short intervals, randomness creates slight variance (jitter), but over hundreds of scheduling ticks, the actual CPU allocation converges exactly to the ratio of tickets held.

Ticket Mechanisms

  • Ticket Currency: A multi-user operating system can allocate 100 global tickets to User Alice and 100 to User Bob. Alice can create three tasks and allocate her local currency among them however she pleases; the kernel converts her local tickets into global lottery shares.
  • Ticket Transfer: A client process communicating with a database server can temporarily transfer its tickets to the server thread while awaiting a query result, ensuring the server executes at high speed on the client's behalf.

Deterministic Fair-Share: Stride Scheduling

To eliminate the random variance of lottery scheduling, Waldspurger created Stride Scheduling:

  • Each process is assigned a stride inversely proportional to its ticket allocation: Stride = Large_Constant / Tickets.
  • Every process tracks its execution progress with a pass counter (initialized to 0).
  • The scheduler always picks the process with the lowest pass value. After it executes for a quantum, its pass value is incremented by its stride: pass += Stride.
  • Stride scheduling produces precisely identical proportional-share allocations to lottery scheduling at every single step, eliminating all statistical jitter.
