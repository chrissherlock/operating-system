02. Interrupts & Direct Memory Access (DMA)

In Module 01, we established the fundamental communication modes between the CPU and hardware controllers. However, high-throughput operating systems cannot rely on naive polling without stalling computation, nor can they handle gigabit streams by processing complex network stacks inside hardware interrupt routines.

This module explores the silicon-level mechanics of Hardware Interrupts, the dual-phase deferral models used by modern kernels to preserve system responsiveness, and the microarchitectural intricacies of Direct Memory Access (DMA) across caching and virtual memory boundaries.

1. Hardware Interrupt Mechanics & The APIC

A hardware interrupt is an asynchronous electrical signal generated by an I/O device controller that forces the CPU to suspend its current instruction pipeline, transition privilege modes, and execute a dedicated kernel routine.

From Legacy PIC to Modern APIC & MSI-X

The architecture of interrupt delivery has undergone a profound evolution:

  • The Legacy 8259A PIC: Early IBM PCs used dual cascaded 8259A Programmable Interrupt Controllers, providing a mere 15 discrete hardware IRQ pins. IRQs were electrically tied to fixed motherboard traces, causing severe conflicts when multiple PCI cards shared interrupt lines.
  • The Advanced Programmable Interrupt Controller (APIC): Standard on modern multiprocessor systems. It splits interrupt coordination into two parts:
    1. I/O APIC: Located on the motherboard chipset or root complex, collecting physical interrupt pins from peripherals and routing them across the system bus as digital messages.
    2. Local APIC: Integrated directly onto each physical CPU core, managing local timer interrupts, inter-processor interrupts (IPIs), and prioritizing incoming device interrupts.
  • Message Signaled Interrupts (MSI / MSI-X): Modern PCIe devices dispense with physical electrical interrupt pins entirely. To raise an interrupt, the peripheral executes a specialized PCIe memory write transaction (MSI-X) directly to a specific physical address mapped to the CPU's local APIC. Devices like NVMe drives and 100 GbE NICs can allocate up to 2,048 independent interrupt vectors, directing traffic from individual hardware queues to specific CPU cores.

The Hardware Execution Sequence on Interrupt

When an interrupt arrives and the CPU's Interrupt Flag (EFLAGS.IF) is set to 1, the processor executes the following indivisible microarchitectural sequence:

  1. Pipeline Suspension: The CPU completes or drains instructions currently retiring in the execution pipeline.
  2. Stack & State Preservation: The CPU switches from the user stack to the privileged Kernel Interrupt Stack (specified in the Task State Segment / Interrupt Stack Table). It pushes the program counter (CS:RIP), processor status register (RFLAGS), and stack pointer (SS:RSP) onto the stack.
  3. Masking Interrupts: The CPU clears EFLAGS.IF = 0, disabling maskable hardware interrupts to prevent nested interrupt reentrancy.
  4. Vector Indexing: The processor uses the interrupt vector number (e.g. 0x42) as an index into the Interrupt Descriptor Table (IDT), loads the target driver's gate descriptor, and jumps to the entry point of the driver's Interrupt Service Routine (ISR).

2. The Dual-Phase Interrupt Model: Top-Half vs. Bottom-Half

Operating system engineers face an acute design conflict when writing device driver interrupt handlers:

The Interrupt Latency Paradox:
  • Requirement 1 (Execute Immediately & Fast): Hardware interrupts execute with local interrupts disabled (or masked at the device's IRQL). If an ISR executes long-running tasks, the CPU cannot service timer ticks, network packets, or audio buffers. Other hardware interrupts will be dropped, causing packet loss and system stutter.
  • Requirement 2 (Perform Substantial Work): When a 10 GbE NIC receives a packet, the operating system must verify IP checksums, parse TCP headers, route through firewall tables, and allocate socket buffers—operations requiring milliseconds of computation, memory allocations, and lock acquisitions.

To resolve this contradiction, all modern operating systems divide interrupt handling into two distinct execution phases:

Phase 1: Top-Half (Hard-IRQ / DIRQL)

Synchronous & Ultra-Brief (< 1 μs)

Executes immediately upon hardware interrupt trigger with interrupts masked.

Responsibilities:

  • Acknowledges the controller (clearing the hardware interrupt bit on the device).
  • Reads hardware status registers and grabs pointer to DMA buffer.
  • Enqueues a deferred execution packet (Softirq, Tasklet, or DPC).
  • Returns immediately to re-enable CPU hardware interrupts!

Phase 2: Bottom-Half (Softirq / DPC)

Asynchronous & Interrupts Enabled

Executes shortly after the Top-Half finishes, but with hardware interrupts fully enabled.

Responsibilities:

  • Processes the heavy payload (TCP/IP checksum verification, memory allocations).
  • Can be preempted by higher-priority hardware interrupts without stalling the machine.
  • Wakes sleeping user-space threads awaiting socket or disk data.

Linux Implementation: Top-Half vs. Softirq / Workqueues

Linux provides three mechanisms for bottom-half deferral:

  • Softirqs: Statically allocated at compile time (e.g. NET_RX_SOFTIRQ, BLOCK_SOFTIRQ). Reentrant across multiple cores concurrently. Executes right before returning to user space or via the kernel thread ksoftirqd/N.
  • Tasklets: Built on top of softirqs, but guaranteed that two instances of the same tasklet will never run simultaneously on different cores (simplifying driver concurrency).
  • Workqueues: Defer execution to true kernel worker threads (kworker/N:M). Because workqueues execute in process context, they are allowed to sleep, allocate memory, and wait on mutexes (unlike softirqs and tasklets, which cannot sleep).

Windows NT Implementation: ISR vs. Deferred Procedure Call (DPC)

Windows NT enforces a strict hierarchy of Interrupt Request Levels (IRQLs):

  • DIRQL (Device IRQL): The hardware ISR runs at DIRQL. Code executing at DIRQL cannot wait on mutexes, touch pageable memory, or allocate RAM. The ISR reads the device registers, copies pointer references, and invokes: 
    KeInsertQueueDpc(&DeviceExtension->DpcObject, NULL, NULL);
  • DISPATCH_LEVEL (DPC): The Windows kernel maintains a per-processor DPC queue. When all DIRQL hardware interrupts clear, the kernel drops the processor IRQL to DISPATCH_LEVEL and executes the queued DPCs. Software at DISPATCH_LEVEL runs with hardware interrupts enabled.

3. Direct Memory Access (DMA) & Cache Coherency

Direct Memory Access allows peripherals to read and write physical RAM directly across the PCIe root complex without routing every word through CPU registers. However, this architectural bypass introduces a major hardware hazard: The Cache Coherency Dilemma.

The Coherency Problem in Non-Coherent Architectures

The CPU reads and writes memory through ultra-fast L1, L2, and L3 caches using write-back policies. When a DMA controller writes a new data packet directly into DRAM:

  • Stale Cache Reads: If CPU Core 0 already holds that memory address cached in its L1 cache, the CPU continues reading the stale cached data, completely oblivious that the DMA engine updated physical DRAM!
  • Cache Overwrite Hazard: If the CPU has modified adjacent variables in its write-back cache, a subsequent cache-line flush can write dirty CPU cache data over the top of the newly arrived DMA packet in DRAM, destroying the network data!
Hardware Bus Snooping vs. Software Maintenance:
  • Hardware Coherent Systems (x86 / Modern Server ARM): The CPU cache controllers monitor (snoop) all DMA transactions on the interconnect. If DMA writes to an address present in L1/L2, the hardware cache controller automatically invalidates or updates the CPU's cache line. Zero software intervention required.
  • Non-Coherent Systems (Embedded ARM, DSPs, Mobile SoCs): The operating system kernel must perform explicit, manual cache synchronization:
    1. Before DMA Read: Kernel flushes (cleans) CPU dirty cache lines to DRAM so the device reads valid data.
    2. Before DMA Write: Kernel invalidates the CPU cache lines over the destination buffer so the CPU is forced to fetch fresh data from DRAM.

The IOMMU: Translation, Isolation, and Virtualization

In modern enterprise systems, DMA engines do not write to raw physical memory addresses directly. Instead, transactions pass through an I/O Memory Management Unit (IOMMU)—known as Intel VT-d, AMD-Vi, or ARM SMMU:

  • Address Translation: Translates Device Virtual Addresses (DVA) into Host Physical Addresses (HPA). This allows a legacy device with 32-bit DMA addressing to write into 64-bit physical memory space, and allows scatter-gather paging without continuous host RAM buffers.
  • Security & Fault Isolation: A buggy or compromised PCIe device could maliciously DMA over kernel memory structures. The IOMMU strictly limits device DMA to specifically mapped pages, protecting kernel integrity.
  • Virtual Machine Passthrough (SR-IOV): Allows a physical PCIe network card or GPU to be assigned directly to a guest Virtual Machine (VM) while ensuring DMA accesses are constrained within the VM's assigned physical memory slice.
