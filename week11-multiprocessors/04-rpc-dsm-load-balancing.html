8.2.4 Remote Procedure Call Semantics & Fault Modes

While standard procedure calls execute within a single address space with uniform pointers and guaranteed returns, Remote Procedure Calls operate over unreliable networks where messages can be dropped, duplicated, or reordered.

Handling Client-Server Failures

Failure Condition Impact Resolution Strategy
Lost Request Message Client hangs indefinitely waiting for a reply that will never arrive. Client sets retransmission timer; resends request upon expiration.
Lost Reply Message Server executed the operation, but the client never received confirmation. Requires Idempotency analysis. Non-idempotent operations must use sequence numbers to avoid re-execution.
Server Crash After Execution Server executes transaction, crashes before network transmission of ack. Client cannot distinguish between pre-execution and post-execution crashes without persistent transaction logs.
Client Crash (Orphan Tasks) Server continues computing on behalf of a client that is no longer running. Orphan elimination algorithms: Extermination, Reincarnation (epoch numbers), or Gentle Expiration.

Invocation Semantics

  • At-Least-Once Semantics: Client retransmits requests until an acknowledgment returns. Guarantees that the call runs at least once, but may execute multiple times if replies are delayed or dropped. Safe only for idempotent operations (e.g., reading a specific file block, setting a balance to a fixed number).
  • At-Most-Once Semantics: Server tracks sequence IDs and filters duplicate requests. Guarantees that the operation runs either once or not at all if the server crashed. Essential for non-idempotent requests (e.g., transferring funds or appending to a ledger).
  • Exactly-Once Semantics: The theoretical ideal where an operation occurs precisely once despite network partitions and node crashes. In practice, achieving this across arbitrary failure modes requires distributed two-phase commit protocols and persistent transaction logging.

8.2.5 Distributed Shared Memory: Consistency Models

Building scalable Distributed Shared Memory requires balancing the illusion of strict memory consistency against network message volume.

1. Sequential Consistency

Defined by Leslie Lamport (1979): A multiprocessor system is sequentially consistent if the result of any execution is the same as if the operations of all processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program. Every write must be visible to all subsequent reads across all nodes immediately, requiring synchronous invalidation round-trips that saturate network bandwidth.

2. Release Consistency

Rather than synchronizing memory on every individual read and write, Release Consistency divides memory accesses into ordinary reads/writes and synchronization operations:

  • Acquire: Informs the system that a critical section is beginning. Memory updates made by other nodes are pulled and validated locally.
  • Ordinary Accesses: Reads and writes occur to local page copies without broadcasting network invalidations.
  • Release: Signals completion of the critical section. All local dirty modifications are propagated out to other nodes holding copies.
Performance Impact: Release consistency batches multiple writes together, exchanging updates only at synchronization boundaries. This drastically reduces network message frequency compared to sequential consistency.

8.2.6 & 8.2.7 Distributed Scheduling & Load Balancing

In a multicomputer, arrival rates across independent nodes fluctuate over time. Dynamic load balancing transfers runnable tasks from heavily loaded machines to lightly loaded machines.

Algorithm Taxonomies

  • Transfer Policy: Determines whether a node is in a suitable state to offload a task (e.g., local run queue length exceeds threshold $T_{\text{high}}$) or receive a task (run queue falls below $T_{\text{low}}$).
  • Location Policy: Identifies which peer node should be chosen as the partner for task migration.
  • Information Policy: Dictates how load metrics are collected across nodes (periodic broadcast vs. demand-driven polling).

Sender-Initiated vs. Receiver-Initiated Probing

Characteristic Sender-Initiated Probing Receiver-Initiated Probing
Initiator Overloaded node with excess tasks. Underloaded or idle node seeking work.
Low System Load Highly efficient: First probe quickly finds an idle node. Inefficient: Many idle nodes probe few busy nodes.
High System Load Probe Storms: Busy nodes flood the network seeking non-existent idle targets. Highly efficient: Idle node immediately finds a heavily loaded partner to offload.
Migration Cost Preemptive or newly spawned tasks can be moved before starting. Usually requires migrating already-executing tasks, incurring context and memory transfer costs.
