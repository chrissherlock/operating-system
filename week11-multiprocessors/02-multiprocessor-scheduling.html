Section 8.1.4

Multiprocessor Scheduling & Security

Timesharing versus spacesharing, cache affinity retention, two-dimensional gang scheduling, and microarchitectural security scheduling.

Timesharing vs. Spacesharing

On a uniprocessor, the scheduler makes one fundamental decision: which thread runs next on the single CPU. On a multiprocessor, scheduling becomes multidimensional: the scheduler must choose which thread to run and which physical CPU core should execute it.

  • Timesharing: Threads share CPU cores over time. Each CPU independently selects runnable threads from a shared or per-core run queue, executing them for a time quantum before switching. Timesharing maximizes utilization when running collections of independent, compute-bound jobs.
  • Spacesharing: Divides physical cores among parallel applications. A parallel job requesting $N$ cores is assigned $N$ dedicated CPUs until termination. No context switches or preemption occur during execution. Spacesharing avoids synchronization latency across parallel threads, but risks underutilization if threads block on I/O.

Affinity Scheduling & Cache Warmth

When thread $T$ executes on CPU 0, it loads working data into CPU 0's private L1 and L2 caches. If the scheduler preempts $T$ and subsequently dispatches it to CPU 1:

  • CPU 1's cache is cold relative to $T$, forcing expensive cache misses to L3 or main memory.
  • CPU 0's cache contains dirty lines that must be invalidated via cache coherence broadcasts when CPU 1 writes them.

Affinity Scheduling mitigates this performance penalty by attempting to reschedule a thread onto the same physical core it previously occupied.

Soft vs. Hard Affinity

Type Mechanism Trade-Off
Soft Affinity The scheduler prefers the previous core, but migrates the thread if the core is busy and another core is idle. Maximizes overall CPU utilization at the cost of periodic cache-cold invalidations.
Hard Affinity The thread is strictly constrained to a designated bitmask of CPUs (e.g., via sched_setaffinity). Ensures deterministic cache locality; can leave cores idle if the pinned thread blocks.

Gang Scheduling (Two-Dimensional Scheduling)

When parallel programs communicate frequently using spinlocks or message barriers, standard independent scheduling causes severe performance collapse.

The Desynchronization Hazard: Suppose Thread 0 sends a message to Thread 1 and spins waiting for an immediate acknowledgment. If Thread 1 is scheduled on another core, it responds in nanoseconds. However, if Thread 1 is currently preempted and waiting in a run queue, Thread 0 spins wasted CPU cycles across its entire time quantum waiting for Thread 1 to be scheduled.

Pioneered by John Ousterhout (1982), Gang Scheduling solves this issue through three invariants:

  1. Groups of related threads form a "gang".
  2. All members of a gang are scheduled simultaneously on distinct physical cores.
  3. All members of a gang begin and terminate their time slices synchronously in lockstep.

Multiprocessor Scheduling for Security

Modern processors frequently deploy Simultaneous Multithreading (SMT), where a single physical execution core presents two or more architectural hardware threads (e.g., Intel Hyper-Threading).

Microarchitectural Side-Channel Attacks (MDS / RIDL / Spectre)

Hardware threads sharing a physical core also share internal microarchitectural structures:

  • L1 Data & Instruction Caches
  • Translation Lookaside Buffers (TLB)
  • Branch Predictor Buffers & Branch Target Buffers (BTB)
  • Microarchitectural Fill Buffers and Line Fill Buffers

If the operating system scheduler pairs an untrusted user process (or malicious container) on Thread 0 while running a sensitive cryptographic service (or kernel system call) on Thread 1 of the exact same physical core, the attacker can observe cache eviction timing or exploit speculative execution side-channels to reconstruct secret keys.

Core Scheduling Mitigations

To neutralize sibling-thread side channels without disabling hyperthreading entirely, modern kernels (including Linux and Windows) implement Core Scheduling:

The Co-Scheduling Invariant: Sibling hardware threads belonging to the same physical core must only execute tasks belonging to the same security domain (e.g., the same process or tasks sharing identical cryptographic credentials). If an isolated task is scheduled on Thread 0, and no sibling task from the same trust group is runnable, Thread 1 is forced to execute an idle halt loop.
