Multiprocessors: Hardware, Cache Coherence & OS Models

Shared-memory architectures, snooping cache protocols, hardware interconnect topologies, and kernel concurrency organizations.

8.1.1 Multiprocessor Hardware

A multiprocessor is a single computer system containing two or more physical CPUs (or CPU cores) that communicate directly by sharing a unified physical memory address space. Any CPU can write a memory address, and any other CPU can subsequently read that address.

1. Uniform Memory Access (UMA) Architecture

In a Uniform Memory Access (UMA) system, every CPU exhibits identical latency and bandwidth when referencing any location in main memory. Three principal interconnect designs achieve UMA:

  • Shared Bus Architecture: CPUs and memory share a single physical bus. While cost-effective, bus bandwidth saturates quickly (typically beyond 2 to 4 processors). CPUs rely on large onboard caches to minimize bus cycles.
  • Crossbar Switch Fabric: Connects $n$ processors to $m$ memory modules using an $n \times m$ matrix of electronic crosspoints. Crosspoints allow simultaneous non-conflicting reads and writes without bus arbitration. However, the hardware footprint scales at $O(n \times m)$, limiting physical scaling.
  • Multistage Switching Networks (Omega Networks): Uses $2 \times 2$ switching elements arranged in $\log_2 n$ stages to route memory requests. Offers an architectural compromise between single-bus bottlenecks and crossbar crosspoint growth.

2. Non-Uniform Memory Access (NUMA) Architecture

To scale beyond dozens of cores without exponential switch costs, modern systems employ Non-Uniform Memory Access (NUMA). In a NUMA machine:

  • Physical memory is partitioned across multiple nodes.
  • Each node contains one or more CPUs, memory controllers, and a portion of the global address space (its local memory).
  • Accessing local memory is fast (e.g., ~50–80 ns). Accessing memory physically attached to a different node over an interconnect link (e.g., Intel UPI, AMD Infinity Fabric) requires traversals that incur noticeably higher latency (e.g., ~150–300 ns).
The NUMA Factor: The ratio of remote memory access latency to local memory access latency is called the NUMA factor. Operating system schedulers and memory allocators must be NUMA-aware to allocate pages and schedule execution within the same NUMA node whenever possible.

Cache Coherence & The MESI Protocol

When multiple CPUs maintain local caches of shared RAM, an inconsistent state arises if CPU A modifies variable $X$ in its local cache while CPU B holds an older copy in its cache. Hardware maintains consistency using Cache Coherence Protocols.

The 4-State MESI Protocol

State Description Memory Clean/Dirty Other Caches Have Copy?
M (Modified) Line is present only in this cache and is dirty (modified). Must be flushed back to RAM on eviction. Dirty No
E (Exclusive) Line is present only in this cache and matches main memory. Can be transitioned to Modified without bus traffic. Clean No
S (Shared) Line is present in this cache and potentially present in other caches. All copies match main memory. Clean Yes (Likely)
I (Invalid) Line contains stale or unallocated data. Reads cause a cache miss. N/A N/A

Concept Overview: Because modern CPU execution cores operate orders of magnitude faster than main memory, each core relies on high-speed private caches (L1 and L2). However, private caches introduce the Cache Coherence Problem: if CPU 0 modifies a variable in its private cache, CPU 1's private cache immediately becomes stale. To preserve memory consistency without routing every access back to slow main RAM, hardware controllers monitor the shared memory bus using the MESI Protocol (Modified, Exclusive, Shared, Invalid). 8.1.2 Multiprocessor Operating System Models

Structuring an operating system to manage multiple concurrent execution cores requires fundamental architectural decisions regarding kernel data structure placement, reentrancy, and synchronization boundaries. Computer architects and OS designers have historically organized multiprocessor operating systems into three distinct models:

1. Each CPU Has Its Own Operating System (Static Partitioning)

The simplest mechanism partitions physical memory into $N$ disjoint regions for $N$ processors. Each core executes an independent, private copy of the operating system kernel with its own run queue, process table, and buffer cache:

  • Zero Kernel Synchronization Contention: Because each OS instance mutates only its private memory space, no multiprocessor locks, spinlocks, or inter-core critical sections are required.
  • Severe Resource Imbalance: Workloads cannot dynamically balance. If CPU 0 has 20 compute-intensive tasks queued while CPUs 1, 2, and 3 are idle, CPU 0 cannot offload threads without complex inter-node IPC.
  • Memory Fragmentation: A file cached in CPU 0's private buffer cache must be duplicated in CPU 1's cache if accessed there, wasting physical RAM.

2. Master-Slave Multiprocessors (Asymmetric Multiprocessing - ASMP)

To enable resource sharing without redesigning uniprocessor kernel algorithms, the master-slave architecture dedicates a single processor (the master, CPU 0) to executing the kernel, device drivers, and I/O interrupts. All other processors (the slaves) run user-space applications exclusively:

  • Simplified Concurrency: Since only CPU 0 ever executes in supervisor mode (Ring 0), kernel tables require no multi-core locking primitives. Slave CPUs never access kernel memory directly.
  • The Master Bottleneck: When user applications on slave CPUs issue system calls (e.g., read(), write(), fork()), they must trap and stall, queuing work requests for the master. As the number of slave cores increases, the master saturates at 100% CPU utilization, leaving worker cores idling in wait states.

3. Symmetric Multiprocessing (SMP)

Modern operating systems implement Symmetric Multiprocessing (SMP), where a single, unified operating system image resides in shared physical memory. Every physical core can execute kernel code, service hardware interrupts, and schedule threads concurrently:

  • Kernel Reentrancy: Multiple CPUs can execute kernel code simultaneously. Two threads executing system calls on different cores can enter the kernel concurrently.
  • Evolution of Locking Granularity:
    • Giant Kernel Lock (Big Kernel Lock / BKL): Early SMP designs placed a single mutex around the entire kernel. While simple, it essentially serialized all system calls, turning the SMP machine back into a master-slave system where only one CPU could execute kernel routines at any time.
    • Fine-Grained Subsystem Locking: Modern SMP kernels partition locking across independent data structures (per-core run queues, per-inode mutexes, lockless Read-Copy-Update (RCU) lists). Two cores modifying different file inodes or scheduling local threads execute in true parallel without lock contention.

8.1.3 Multiprocessor Synchronization & Cache Contention

On a single-core uniprocessor system, an operating system kernel achieves mutual exclusion across short critical sections simply by disabling hardware interrupts. Because only one thread of execution exists, disabling interrupts prevents the timer tick from preemption, ensuring atomicity.

On a multiprocessor, disabling interrupts on CPU 0 has zero effect on CPU 1, 2, or 3. Sibling cores continue fetching instructions, accessing shared data structures, and causing race conditions. Multiprocessors require dedicated hardware-level atomic synchronization primitives.

1. Hardware Atomic Primitives

On a single-core uniprocessor, mutual exclusion can be achieved simply by disabling hardware interrupts to prevent timer preemption. On a multiprocessor, disabling interrupts on Core 0 has zero effect on Core 1, which continues executing instructions and mutating memory concurrently.

If an operating system attempts to implement a mutual exclusion lock using standard, non-atomic software read and write instructions, a race condition occurs whenever two cores attempt to claim the lock simultaneously:

// NON-ATOMIC SOFTWARE FAILURE: Race window between read and write int Naive_Acquire(volatile int *lock) { if (*lock == 0) { // Core 0 and Core 1 both read 0 simultaneously! *lock = 1; // Both write 1 and believe they own the lock return 1; // Mutual exclusion violated: both enter critical section! } return 0; }

To eliminate this vulnerability, processor architectures provide Atomic Read-Modify-Write (RMW) Instructions. These instructions guarantee that reading the old value and writing the new value occur as an indivisible, single-cycle operation across the entire memory hierarchy. Hardware guarantees this either by asserting the physical bus LOCK# signal or by maintaining exclusive ownership of the cache line via the cache coherence protocol:

// 1. ATOMIC TEST-AND-SET (x86-64: LOCK BTS or XCHG) // Atomically swaps 1 into *lock and returns the old value in a single bus transaction int Atomic_TestAndSet(volatile int *lock) { int old_val; __asm__ volatile ( "lock xchgl %0, %1" : "=r" (old_val), "+m" (*lock) : "0" (1) : "memory" ); return old_val; // Returns 0 on successful lock acquisition, 1 on busy } // 2. ATOMIC COMPARE-AND-SWAP / CAS (x86-64: LOCK CMPXCHG) // Updates *addr to new_val ONLY IF it currently holds expected_val bool Atomic_CompareAndSwap(volatile int *addr, int expected_val, int new_val) { unsigned char success; __asm__ volatile ( "lock cmpxchgl %3, %1;\n\t" "sete %0" : "=q" (success), "+m" (*addr), "+a" (expected_val) : "r" (new_val) : "memory" ); return (bool)success; }

2. The Cache-Line Bouncing Hazard

While spinlocks avoid the expensive latency of a context switch (~1,000–5,000 CPU cycles) for short critical sections, naive spinlocks cause severe hardware degradation:

The Invalidation Storm: When multiple CPUs execute TestAndSet(&lock) in a tight while-loop, every execution is an atomic write operation. To execute an atomic write, the CPU's cache controller must obtain the cache line in the Modified (M) state, broadcasting a BusUpgr or BusRdX invalidation across the memory bus. When 4 cores spin simultaneously, the cache line bounces continuously between CPU caches, saturating the bus and starving normal data accesses.

3. Optimization: Test-and-Test-and-Set (TTAS)

To prevent memory bus saturation, lock designers utilize Test-and-Test-and-Set (TTAS). Instead of blindly issuing atomic writes on every iteration, a spinning CPU first reads the lock using ordinary memory read instructions:

  • While the lock is held (1), the core spins reading its local cache line in the Shared (S) state. Normal reads produce zero bus traffic!
  • Only when the lock holder releases the lock (writing 0) is the shared cache line invalidated.
  • The spinning cores then execute an atomic TestAndSet to claim the freed lock.
