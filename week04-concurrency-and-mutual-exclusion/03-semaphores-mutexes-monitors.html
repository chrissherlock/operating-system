03. Sleep/Wakeup, Semaphores & Monitors

Spinlocks and hardware atomic instructions provide the fundamental building blocks of synchronization, but they suffer from a crippling operational drawback: busy waiting.

While a thread spins in a while loop waiting for a lock, it burns 100% of its CPU time slice doing zero productive work. If the thread holding the lock is blocked waiting for disk I/O, network packets, or timer events, spinning on the CPU achieves nothing.

To build scalable systems, operating systems introduce blocking synchronization primitives: mechanisms that transition waiting threads out of the CPU execution pipeline and into the BLOCKED queue until the required condition is fulfilled.

1. Sleep & Wakeup: The Lost Wakeup Hazard

In Module 02, we explored how hardware atomic instructions enable spinlocks. While spinlocks provide rapid mutual exclusion for tiny, nanosecond critical sections on multiprocessor systems, they suffer from a fatal operational defect: busy waiting.

A spinning thread burns 100% of its CPU time slice executing instructions that achieve zero computational work. If the thread holding the lock is descheduled, preempted, or waiting on a slow peripheral (such as an NVMe disk read, network packet, or user keystroke), all competing threads on other cores spin fruitlessly, driving system temperature and power consumption to maximum while stalling progress.

To build scalable operating systems, software requires blocking primitives: mechanisms that allow a thread to release its CPU execution core voluntarily, enter a suspended state (BLOCKED or WAITING), and sleep until another execution thread notifies it that the desired event or resource has become available.

The Primitive Sleep and Wakeup Abstraction

The earliest blocking synchronization models relied on a pair of paired operating system primitives:

  • sleep(): An atomic system call that causes the invoking process to suspend execution. The kernel removes the process from the scheduler's READY runqueue, updates its state to BLOCKED, and context-switches to another runnable thread.
  • wakeup(pid): A system call taking a target process identifier (PID) as an argument. The kernel locates the target process's Process Control Block (PCB) and transitions its state from BLOCKED back to READY, placing it back onto the scheduler's runqueue.

The Classical Bounded-Buffer Producer-Consumer Model

To evaluate sleep() and wakeup(), consider the canonical Producer-Consumer problem (also called the Bounded-Buffer problem). Two processes share a common fixed-size buffer of capacity N:

  • The Producer generates data items and deposits them into the buffer.
  • The Consumer extracts data items from the buffer and consumes them.
  • A shared integer variable count tracks the number of items currently residing in the buffer (initialized to 0).
/* FLAWED: Producer-Consumer Implementation Using Primitive Sleep and Wakeup */
#define N 100                   /* Number of slots in the shared buffer */
volatile int count = 0;         /* Number of data items currently in buffer */

void producer(void) {
    while (true) {
        item_t item = produce_item(); /* Generate next data item */

        if (count == N) {
            sleep();            /* Buffer is full: producer sleeps */
        }

        insert_item(item);      /* Deposit item into buffer */
        count++;                /* Increment item counter */

        if (count == 1) {
            wakeup(consumer_pid); /* Was empty: wake up sleeping consumer */
        }
    }
}

void consumer(void) {
    while (true) {
        if (count == 0) {
            sleep();            /* Buffer is empty: consumer sleeps */
        }

        item_t item = remove_item(); /* Extract item from buffer */
        count--;                /* Decrement item counter */

        if (count == N - 1) {
            wakeup(producer_pid); /* Was full: wake up sleeping producer */
        }

        consume_item(item);     /* Process the data item */
    }
}

The Anatomy of the Lost Wakeup Defect

This intuitive code contains a fatal synchronization flaw known as the Lost Wakeup Problem. The defect arises because the high-level test of count and the execution of sleep() are not atomic.

Figure 3.1: The Lost Wakeup Race Window Execution Timeline
How preemption between condition testing and the sleep() system call causes signals to vanish permanently.
Step-by-Step Breakdown of the Race Interleaving:
  1. Evaluation (Consumer): The buffer is currently empty (count == 0). The Consumer executes if (count == 0). The condition evaluates to true. The Consumer prepares to execute sleep().
  2. Preemptive Interruption: Immediately after the comparison but before the CPU can execute the system call trap instruction for sleep(), the local APIC hardware timer generates an interrupt. The OS kernel context-switches from the Consumer to the Producer.
  3. Production & Signal (Producer): The Producer runs. It produces an item, inserts it into slot 0, and increments count from 0 to 1.
  4. The Stateless Wakeup Call: The Producer tests if (count == 1). Finding it true, the Producer calls wakeup(consumer_pid).
  5. The Silent Signal Loss: Inside the kernel, the dispatcher looks up the Consumer's process entry. Because the Consumer was interrupted before calling sleep(), the Consumer is not sleeping—it is in the READY state on the runqueue! A primitive wakeup signal has no memory buffer; because the process is not in the BLOCKED state, the wakeup signal is discarded by the kernel and permanently lost.
  6. The Fatal Sleep (Consumer): The Consumer is rescheduled. Its program counter resumes exactly where it was paused: at the sleep() instruction. It executes sleep(), moving its PCB to the BLOCKED queue. The Consumer is now asleep, waiting for a wakeup signal that was already delivered and lost.
  7. Complete System Deadlock: The Producer continues executing cycles, generating items and incrementing count. Because the Consumer is asleep, no items are ever removed. Eventually, the buffer fills completely (count == N). The Producer tests if (count == N), finds it true, and calls sleep().

Result: Total, unrecoverable deadlock. Both processes are permanently asleep, neither can run to wake the other, and no exception, crash log, or fault is raised by the operating system.

The Failed Wakeup-Waiting Bit Patch

An intuitive early attempt to patch this flaw was to equip each process control block with a wakeup waiting bit:

  • When a wakeup() signal was sent to a process that was not yet asleep, the kernel set the target's wakeup waiting bit to 1.
  • When a process called sleep(), the kernel checked this bit. If the bit was 1, the kernel cleared the bit to 0 and allowed the process to continue running without sleeping.
Why the Wakeup Waiting Bit Fails:
While a 1-bit memory prevents signal loss for two single-threaded processes under a single missed wakeup, it collapses completely under multi-process concurrency:
  • If three producers attempt to wake a consumer while it is preempted, the wakeup waiting bit is set to 1 on the first wakeup, but cannot represent the second or third wakeup (it saturates at 1).
  • Subsequent signals are lost, re-introducing the identical deadlock when multiple items are deposited.
This realization forced computer scientists to recognize a fundamental truth: synchronization primitives cannot be stateless boolean flags; they must be atomic integer counters equipped with FIFO wait queues—the exact definition of Dijkstra's Semaphore.

2. Dijkstra's Semaphores (1965)

In 1965, Dutch computer scientist Edsger W. Dijkstra introduced the Semaphore in his pioneering work on the THE multiprogramming system. The semaphore permanently resolved the lost wakeup problem by replacing stateless signaling pulses with an atomic integer variable coupled with a sleep queue.

A semaphore is not simply a flag; it is an abstract data type with historical memory. It maintains an integer counter that records wakeups sent in the past for consumption in the future.

The Fundamental Atomic Primitives: P() and V()

In Dijkstra's original Dutch notation, the two fundamental operations were named P and V:

  • P() (from proberen, "to test"): Often called down() or wait(). Decrements the semaphore value and blocks the calling thread if resources are unavailable.
  • V() (from verhogen, "to increment"): Often called up(), signal(), or post(). Increments the semaphore value and wakes a sleeping thread if any are queued.

How an internal spinlock protects the atomic integer counter and FIFO wait queue during down() and up() calls.

Mathematical Models: Classical Non-Negative vs. Signed Model

Operating system literature and production kernels define the integer counter behavior using two mathematical conventions:

1. Classical Non-Negative Model

In Dijkstra's original specification:

  • The value of s is never negative (s ≥ 0).
  • If s > 0, down() decrements s and proceeds.
  • If s == 0, down() suspends the thread on the wait queue without decrementing.
  • The queue length is tracked as a separate count in the wait queue list.

2. Modern Signed Model (Linux / POSIX)

In modern operating system kernels:

  • The value of s can become negative.
  • down() always decrements s unconditionally. If s < 0, the thread is enqueued and blocked.
  • The Mathematical Invariant: When s < 0, the absolute value |s| represents the exact number of threads currently sleeping on the wait queue.
  • up() increments s. If s ≤ 0, at least one thread is sleeping and must be awakened.

The Implementation Paradox: Spinlocks Inside Sleep Locks

Students frequently encounter a conceptual puzzle: "If semaphores exist to eliminate busy waiting, how do we make the semaphore's own down() and up() routines atomic without busy waiting?"

The answer reveals a fundamental engineering pattern in kernel design: we use a spinlock to implement a sleep lock. 

/* Production Kernel Semaphore Implementation */
typedef struct {
    spinlock_t lock;            /* Hardware spinlock protecting this struct */
    int count;                  /* Resource permit counter */
    struct list_head wait_list; /* FIFO queue of sleeping task_struct PCBs */
} semaphore_t;

void down(semaphore_t *sem) {
    spin_lock(&sem->lock);      /* 1. Acquire spinlock: protect counter and list */

    sem->count--;
    if (sem->count < 0) {
        /* 2. Enqueue calling thread into semaphore wait list */
        enqueue_current_task(&sem->wait_list);
        set_current_task_state(TASK_UNINTERRUPTIBLE);

        spin_unlock(&sem->lock);/* 3. RELEASE spinlock BEFORE invoking scheduler! */
        schedule();             /* 4. Voluntary context switch: thread sleeps */
        return;
    }

    spin_unlock(&sem->lock);    /* Resource acquired immediately; release spinlock */
}

void up(semaphore_t *sem) {
    spin_lock(&sem->lock);      /* 1. Acquire spinlock */

    sem->count++;
    if (sem->count ≤ 0) {
        /* 2. Dequeue first sleeping thread from FIFO list */
        struct task_struct *task = dequeue_task(&sem->wait_list);
        wake_up_task(task);     /* 3. Transition PCB to TASK_RUNNING */
    }

    spin_unlock(&sem->lock);    /* 4. Release spinlock */
}
Why This Does Not Re-Introduce Busy Waiting Waste:
The internal spinlock (sem->lock) is held only for the dozens of nanoseconds required to decrement an integer and insert a pointer into a linked list. It is never held across the schedule() system call.
Therefore, competing cores spin for at most a few dozen clock cycles, rather than spinning for milliseconds while a thread performs disk I/O.

Taxonomy of Semaphore Use Cases

Depending on initial configuration, semaphores fulfill three distinct architectural roles:

1. Binary Semaphores (Mutexes)
  • Initialization: Initialized to 1.
  • Behavior: Constrained to values 1 (unlocked) and 0 (locked). Ensures that only one thread can execute within a critical section at any instant.
  • Critical Architectural Distinction (Binary Semaphore vs. Mutex): In modern systems, a true Mutex has ownership semantics: only the thread that called lock() is legally allowed to call unlock(). If a thread attempts to unlock a mutex it does not own, the kernel throws an exception. Furthermore, mutexes support Priority Inheritance to eliminate priority inversion.
    In contrast, a semaphore has no concept of ownership: any thread (or even an asynchronous hardware interrupt service routine) can call up() to signal and release a binary semaphore.
2. Counting Semaphores (Resource Pool Management)
  • Initialization: Initialized to N, where N > 1 represents the total number of identical units in a shared resource pool.
  • Applications: Database connection pools (e.g., maximum 50 concurrent PostgreSQL connections), DMA buffer slots, or memory allocation pools. Each down() allocates a permit; each up() returns a permit to the pool. When all permits are exhausted, subsequent requesters block automatically.
3. Signaling & Rendezvous Semaphores
  • Initialization: Initialized to 0.
  • Applications: Enforcing strict sequential ordering between asynchronous execution flows. Thread B calls down() and blocks immediately. Thread A carries out hardware initialization or loads data from disk, and then executes up(). This guarantees that Thread B cannot execute its post-requisite code until Thread A has completed its pre-requisite code.

3. Kernel Sleep Queues & Linux Futexes

In Section 2, we analyzed how the operating system kernel implements semaphores and sleep locks using internal spinlocks to guard wait queues. However, that design introduces a major performance bottleneck for user-space applications: every lock acquisition and release requires a kernel system call.

A system call trap instruction (syscall on x86-64, svc on ARM) forces the processor through an involuntary privilege boundary transition from Ring 3 (User Space) to Ring 0 (Kernel Mode). The CPU flushes pipeline queues, changes the stack pointer to the kernel stack, updates page-table permissions, and validates parameters. This sequence consumes 100 to 300 nanoseconds per invocation.

The Empirical Uncontended Invariant

Extensive benchmarking of production software (databases, web servers, GUI toolkits) reveals a universal concurrency profile:

The 90-99% Uncontended Rule:
In well-architected multi-threaded programs, over 90% to 99% of all mutex lock acquisitions encounter zero contention. The lock is free when the thread requests it, and no other thread is attempting to acquire it at that exact instant.

Paying a 200 ns system call penalty millions of times per second just to set an uncontended integer flag in memory is an immense waste of CPU cycles. Conversely, relying purely on spinlocks in user space wastes entire scheduling quanta when a lock is contended.

To bridge this performance divide, Rusty Russell, Ulrich Drepper, and Ingo Molnar engineered the Futex (Fast Userspace Mutex) for the Linux kernel.

The Futex Architecture: Fast-Path vs. Slow-Path

A futex is not an individual kernel object created with an explicit allocation API; it is an ordinary 32-bit integer variable allocated directly in the application's user-space virtual memory.

The core philosophy of the futex subsystem is strict separation of concerns:

  1. The Fast Path (Uncontended — Pure User Space): When a thread wants to acquire a lock, it executes an atomic Compare-and-Swap (cmpxchg) directly on the 32-bit integer in user memory. If the lock was free (0), CAS sets it to 1 (held) and returns immediately.
    Zero system calls, zero kernel entries, executing in ~5 nanoseconds.
  2. The Slow Path (Contended — Kernel Fallback): Only if the atomic CAS fails (because the lock is already held) does the thread fall back to the kernel. The thread invokes the futex() system call, asking the kernel to suspend the calling thread on a sleep queue until the lock holder wakes it.
  3. The Unlock Path: When unlocking, the thread atomically decrements or clears the integer. If no other threads are waiting, the unlock finishes in user space (~5 ns). If waiting threads are detected, the thread issues a futex() system call instructing the kernel to wake the sleeping threads.
Figure 3.3: The Linux Futex Dual-Domain Architecture
How user-space atomic CAS handles uncontended paths in nanoseconds while kernel hash buckets manage sleeping threads.

The Multiplexed System Call: FUTEX_WAIT and FUTEX_WAKE

The Linux kernel exposes the futex subsystem through a single multiplexed system call: 

#include <linux/futex.h>
#include <sys/syscall.h>
#include <unistd.h>

long syscall(SYS_futex, uint32_t *uaddr, int futex_op, uint32_t val,
             const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3);

The two most critical operations defined by futex_op are:

1. FUTEX_WAIT: The Atomic Check-and-Sleep Primitive
syscall(SYS_futex, uaddr, FUTEX_WAIT, val, timeout, NULL, 0);

This command asks the kernel: "If the integer at *uaddr still equals val, put my thread to sleep. If *uaddr != val, do not sleep; return immediately."

How FUTEX_WAIT Completely Eliminates the Lost Wakeup Defect:
Recall from Section 1 that primitive sleep() caused lost wakeups because a thread could be preempted between checking the condition and sleeping.
The kernel's implementation of FUTEX_WAIT guarantees atomicity between checking memory and sleeping:
  1. The kernel pins the physical memory page backing uaddr and hashes the physical address to find the corresponding kernel wait bucket.
  2. The kernel acquires the bucket's internal spinlock: spin_lock(&bucket->lock).
  3. While holding the spinlock, the kernel dereferences uaddr. If another thread unlocked the mutex in user space while the calling thread was entering the kernel (such that *uaddr != val), the kernel aborts the sleep operation immediately, unlocks the bucket, and returns -EWOULDBLOCK.
  4. If and only if *uaddr == val, the calling thread is added to the bucket's wait queue, its state is changed to TASK_INTERRUPTIBLE, the bucket spinlock is released, and schedule() is invoked.
A wakeup signal can never be lost because the check and the enqueue occur atomically under the kernel bucket lock!
2. FUTEX_WAKE: Waking Waiters
syscall(SYS_futex, uaddr, FUTEX_WAKE, val, NULL, NULL, 0);

This command instructs the kernel to look up the bucket associated with uaddr, dequeue up to val threads (typically val = 1 for mutexes, or val = INT_MAX for broadcast signals), and transition them to TASK_RUNNING.

Building a Minimal Production Futex Mutex

Using FUTEX_WAIT and FUTEX_WAKE, we can construct an industrial-grade user-space mutex using a tri-state integer protocol:

  • 0: Lock is free (unlocked).
  • 1: Lock is held by a thread, and no other threads are waiting.
  • 2: Lock is held by a thread, and one or more threads are sleeping in the kernel.
typedef struct {
    uint32_t val; /* 0 = Free, 1 = Held (no waiters), 2 = Held (waiters exist) */
} futex_mutex_t;

void futex_mutex_lock(futex_mutex_t *m) {
    uint32_t c;

    /* 1. FAST PATH: Attempt to atomically transition 0 -> 1 */
    if (__atomic_compare_exchange_n(&m->val, &(c = 0), 1, false,
                                    __ATOMIC_ACQUIRE, __ATOMIC_RELAXED)) {
        return; /* Acquired immediately in user space! ~5 ns */
    }

    /* 2. SLOW PATH: Contention detected */
    do {
        /* If already 2, or if we transition 1 -> 2: announce waiters exist */
        if (c == 2 || __atomic_compare_exchange_n(&m->val, &(c = 1), 2, false,
                                                   __ATOMIC_ACQUIRE, __ATOMIC_RELAXED)) {
            /* Sleep in the kernel only if value is still 2 */
            syscall(SYS_futex, &m->val, FUTEX_WAIT, 2, NULL, NULL, 0);
        }
        /* Upon wakeup, attempt to claim the lock while setting state to 2 */
    } while (__atomic_exchange_n(&m->val, 2, __ATOMIC_ACQUIRE) != 0);
}

void futex_mutex_unlock(futex_mutex_t *m) {
    /* 1. FAST PATH: If value was 1, no waiters exist. Atomically set to 0 */
    if (__atomic_exchange_n(&m->val, 0, __ATOMIC_RELEASE) == 1) {
        return; /* Released in user space! Zero system calls */
    }

    /* 2. SLOW PATH: Value was 2 (waiters exist). Wake up 1 sleeping thread */
    syscall(SYS_futex, &m->val, FUTEX_WAKE, 1, NULL, NULL, 0);
}

Advanced Futex Primitives: Requeueing and Priority Inheritance

Modern implementations of pthread_mutex_t and pthread_cond_t rely on two specialized extensions to the futex system call:

1. The Thundering Herd & FUTEX_REQUEUE

When multiple threads are waiting on a condition variable (e.g. pthread_cond_broadcast()), waking all 100 threads simultaneously causes a thundering herd storm: all 100 threads wake up, enter user space, and immediately contend for the associated mutex. Exactly one thread acquires the mutex, and the remaining 99 threads are immediately forced to issue FUTEX_WAIT to go back to sleep!

To prevent this, Linux provides FUTEX_CMP_REQUEUE: 

syscall(SYS_futex, cond_uaddr, FUTEX_CMP_REQUEUE, 1, (void*)INT_MAX, mutex_uaddr, expected_val);

The kernel wakes exactly one thread on cond_uaddr, and directly shifts all other 99 waiting threads from the condition variable's hash bucket queue over to the mutex's hash bucket queue inside the kernel without waking them into user space.

2. Priority Inheritance Futexes (FUTEX_LOCK_PI)

For real-time systems vulnerable to priority inversion (as explored in Module 02), the Linux kernel provides PI-futexes:

  • The lower 29 bits of uaddr store the Thread ID (TID) of the lock-owning task.
  • If a high-priority thread blocks on FUTEX_LOCK_PI, the kernel inspects the TID in uaddr and temporarily boosts the scheduling priority of the owner task to match the waiter's priority.
  • Once the owner releases the lock via FUTEX_UNLOCK_PI, the kernel drops the owner's priority back to its nominal level.

4. Monitors & Condition Variables

While semaphores are mathematically robust, they are prone to catastrophic human error:

  • A programmer who accidentally writes down(&mutex) followed by another down(&mutex) deadlocks the thread with itself.
  • A programmer who forgets an up(&mutex) leaves the critical region permanently locked.
  • Reversing the order of semaphore operations in complex multi-semaphore code triggers instant deadlocks.

To eliminate these programmer errors, C. A. R. Hoare (1974) and Per Brinch Hansen (1975) developed Monitors.

What is a Monitor?

A Monitor is a high-level programming language construct (native to Java, C#, Ada) that encapsulates shared variables, procedures, and synchronization:

  • Compiler-Enforced Mutual Exclusion: The language compiler automatically ensures that only one thread can be actively executing inside any method of a monitor at any given instant.
  • Threads call monitor methods normally; the compiler injects lock acquisition at method entry and lock release at method exit.

Condition Variables: wait() and signal()

When a thread inside a monitor cannot proceed (e.g., the buffer is full), it cannot simply sleep while holding the monitor lock, because no other thread could ever enter to produce items!

Monitors solve this with Condition Variables (e.g., cond_t):

  • wait(&cond, &mutex): Atomically releases the monitor lock and suspends the calling thread on the condition variable's queue. When awakened, it automatically reacquires the lock before returning.
  • signal(&cond): Wakes up exactly one thread waiting on the condition variable.

Hoare Semantics vs. Mesa Semantics

When a thread calls signal(&cond), which thread runs next? This question divides synchronization theory into two distinct schools:

Hoare Semantics (Signal-and-Wait)

The signaling thread immediately yields the CPU and transfers execution directly to the awakened thread.

Advantage: The condition is guaranteed to be true when the awakened thread runs, allowing simple if (!condition) wait() checks.

Disadvantage: Requires two immediate, costly context switches.

Mesa Semantics (Signal-and-Continue)

The signaling thread retains the CPU and continues running. The awakened thread is moved to the READY queue.

Advantage: Exceptional throughput; used by POSIX pthreads, Java, C++, and Linux.

The Invariant: Another thread might enter and invalidate the condition before the awakened thread runs. Therefore, threads MUST re-check conditions in a while loop: 

while (!condition) {
    pthread_cond_wait(&cond, &mutex);
}
