03. Sleep/Wakeup, Semaphores & Monitors

Spinlocks and hardware atomic instructions provide the fundamental building blocks of synchronization, but they suffer from a crippling operational drawback: busy waiting.

While a thread spins in a while loop waiting for a lock, it burns 100% of its CPU time slice doing zero productive work. If the thread holding the lock is blocked waiting for disk I/O, network packets, or timer events, spinning on the CPU achieves nothing.

To build scalable systems, operating systems introduce blocking synchronization primitives: mechanisms that transition waiting threads out of the CPU execution pipeline and into the BLOCKED queue until the required condition is fulfilled.

1. Sleep & Wakeup: The Lost Wakeup Hazard

The simplest blocking mechanism relies on a pair of system calls:

  • sleep(): Suspends the caller, transitioning it to BLOCKED until another process wakes it up.
  • wakeup(pid): Takes a target process and transitions it from BLOCKED back to READY.

The Producer-Consumer Vulnerability

Consider two processes coordinating over a shared bounded buffer using an integer variable count: 

/* FLAWED: Primitive Sleep and Wakeup Implementation */
int count = 0;
const int N = 100; /* Buffer capacity */

void producer() {
    while (true) {
        item_t item = produce_item();
        if (count == N) sleep(); /* Buffer full: sleep */
        insert_item(item);
        count++;
        if (count == 1) wakeup(consumer_pid); /* Wake consumer if buffer was empty */
    }
}

void consumer() {
    while (true) {
        if (count == 0) sleep(); /* Buffer empty: sleep */
        item_t item = remove_item();
        count--;
        if (count == N - 1) wakeup(producer_pid); /* Wake producer if buffer was full */
        consume_item(item);
    }
}
The Lost Wakeup Defect:
Notice the race condition on count:
  1. The buffer is empty (count == 0). The Consumer runs, checks if (count == 0), and finds it true.
  2. Preemption: Right before the Consumer can execute sleep(), the timer interrupt fires! The Consumer is descheduled.
  3. The Producer runs. It produces an item, places it in the buffer, and increments count to 1.
  4. The Producer checks if (count == 1). It evaluates to true, so the Producer sends wakeup(consumer_pid).
  5. The Disaster: Because the Consumer was preempted before it went to sleep, it is not yet sleeping! The wakeup signal is lost forever.
  6. The Consumer resumes execution. It executes sleep() and enters the BLOCKED state.
  7. The Producer continues producing items until the buffer reaches count == N, at which point the Producer also executes sleep().
Result: Total Deadlock. Both the Producer and Consumer sleep permanently, waiting for wakeups that will never arrive.

2. Dijkstra's Semaphores (1965)

In 1965, Edsger Dijkstra solved the lost wakeup hazard by inventing the Semaphore.

A semaphore is not merely a signal; it is an atomic integer variable with historical memory. It tracks how many wakeups have been saved for future use. A semaphore s supports only two atomic operations:

1. down() (also called P() or wait())

void down(semaphore *s) {
    /* Atomic Silicon Transaction */
    s->value--;
    if (s->value < 0) {
        /* Add calling thread to s->wait_queue */
        block_calling_thread();
    }
}

If s->value > 0, the decrement succeeds and the thread continues executing without sleeping. If s->value ≤ 0, the thread is suspended and appended to the semaphore's wait queue.

2. up() (also called V() or signal())

void up(semaphore *s) {
    /* Atomic Silicon Transaction */
    s->value++;
    if (s->value ≤ 0) {
        /* Remove one thread from s->wait_queue */
        wakeup_thread();
    }
}

The up() operation increments the counter. If any threads are sleeping on the semaphore, exactly one thread is removed from the wait queue and transitioned to READY.

Why Semaphores Completely Eliminate the Lost Wakeup Defect:
Unlike a naked wakeup() call (which vanishes into thin air if no process is sleeping), an up() operation increments the semaphore's integer value.
If the Producer calls up() while the Consumer is preempted, s->value increments from 0 to 1. When the Consumer resumes and calls down(), it decrements 1 to 0 and continues executing without sleeping. The wakeup is never lost!

Binary Semaphores (Mutexes) vs. Counting Semaphores

  • Binary Semaphore (Mutex): Initialized to 1. Its value is constrained to 0 or 1. Used strictly to guarantee mutual exclusion across a single critical section.
  • Counting Semaphore: Initialized to N (e.g., buffer size). Tracks available units of a finite resource pool (e.g., 100 database connections, 16 audio DMA channels).

3. Kernel Sleep Queues & Linux Futexes

In a pure user-space application, calling the operating system kernel for every single mutex lock/unlock incurs massive overhead:

  • Entering the kernel via a trap instruction (syscall) forces a pipeline flush, privilege ring transition, and kernel stack setup, consuming 100–300 nanoseconds per invocation.
  • In real-world software, over 90% of mutex acquisitions are uncontended (no other thread currently holds the lock). Paying a kernel trap penalty for an uncontended lock destroys performance.

The Linux Futex (Fast Userspace Mutex) Architecture

To solve this, Ulrich Drepper and Ingo Molnar engineered the Futex:

  1. The Fast Path (Uncontended — Pure Userspace): The thread uses an atomic Compare-and-Swap (cmpxchg) to test and claim an integer in user-space virtual memory. If the lock was free (0), CAS sets it to 1 and returns immediately. Zero kernel traps, zero system calls, executing in ~5 nanoseconds.
  2. The Slow Path (Contended — Kernel Fallback): If CAS fails because the lock is already held, the thread drops into the kernel via the system call: 
    sys_futex(uaddr, FUTEX_WAIT, val, timeout, NULL, 0);
    The kernel verifies that *uaddr == val (preventing race conditions) and suspends the thread on a kernel-managed hash bucket queue.
  3. The Unlock Path: When unlocking, the thread atomically resets the user-space integer. If waiters are detected, it invokes sys_futex(uaddr, FUTEX_WAKE, 1) to wake the next queued thread.

4. Monitors & Condition Variables

While semaphores are mathematically robust, they are prone to catastrophic human error:

  • A programmer who accidentally writes down(&mutex) followed by another down(&mutex) deadlocks the thread with itself.
  • A programmer who forgets an up(&mutex) leaves the critical region permanently locked.
  • Reversing the order of semaphore operations in complex multi-semaphore code triggers instant deadlocks.

To eliminate these programmer errors, C. A. R. Hoare (1974) and Per Brinch Hansen (1975) developed Monitors.

What is a Monitor?

A Monitor is a high-level programming language construct (native to Java, C#, Ada) that encapsulates shared variables, procedures, and synchronization:

  • Compiler-Enforced Mutual Exclusion: The language compiler automatically ensures that only one thread can be actively executing inside any method of a monitor at any given instant.
  • Threads call monitor methods normally; the compiler injects lock acquisition at method entry and lock release at method exit.

Condition Variables: wait() and signal()

When a thread inside a monitor cannot proceed (e.g., the buffer is full), it cannot simply sleep while holding the monitor lock, because no other thread could ever enter to produce items!

Monitors solve this with Condition Variables (e.g., cond_t):

  • wait(&cond, &mutex): Atomically releases the monitor lock and suspends the calling thread on the condition variable's queue. When awakened, it automatically reacquires the lock before returning.
  • signal(&cond): Wakes up exactly one thread waiting on the condition variable.

Hoare Semantics vs. Mesa Semantics

When a thread calls signal(&cond), which thread runs next? This question divides synchronization theory into two distinct schools:

Hoare Semantics (Signal-and-Wait)

The signaling thread immediately yields the CPU and transfers execution directly to the awakened thread.

Advantage: The condition is guaranteed to be true when the awakened thread runs, allowing simple if (!condition) wait() checks.

Disadvantage: Requires two immediate, costly context switches.

Mesa Semantics (Signal-and-Continue)

The signaling thread retains the CPU and continues running. The awakened thread is moved to the READY queue.

Advantage: Exceptional throughput; used by POSIX pthreads, Java, C++, and Linux.

The Invariant: Another thread might enter and invalidate the condition before the awakened thread runs. Therefore, threads MUST re-check conditions in a while loop: 

while (!condition) {
    pthread_cond_wait(&cond, &mutex);
}
