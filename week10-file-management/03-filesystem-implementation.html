03. File-System Implementation

Tanenbaum Chapter 4.3: Physical Layouts, Storage Allocation Models, Directory Records, Virtual File Systems, and Journaling.

4.3.1 File-System Layout

File systems are stored on non-volatile disks, solid-state drives, or partitions. Physical storage devices divide raw media into fixed-size physical sectors (typically 512 bytes or 4096 bytes). Operating system file systems group these physical sectors into larger logical blocks (clusters), typically ranging from 1 KB to 64 KB, to balance metadata overhead against internal fragmentation.

1. Partitioning & Boot Records

Before a filesystem can be initialized, a storage drive is segmented into one or more partitions. Sector 0 of the entire physical disk contains the Master Boot Record (MBR) or the primary GUID Partition Table (GPT):

  • Master Boot Record (MBR): Contains bootstrap executable code executed by the BIOS, along with a 64-byte partition table defining the boundaries and types of up to four primary partitions.
  • GPT / UEFI: Modern replacement for MBR supporting 64-bit logical block addressing, redundant partition headers, CRC32 checksums, and globally unique partition identifiers.

2. On-Disk Structural Regions

When a partition is formatted (for instance, via mkfs), the operating system initializes several distinct functional regions laid out sequentially across the partition blocks:

  1. Boot Block: The first block of the partition. Contains partition-specific bootstrap code read into memory by the MBR/UEFI to launch the target operating system.
  2. Superblock: The central administrative descriptor storing filesystem type, block counts, i-node counts, and volume health state.
  3. Free Space Management: Data structures tracking unallocated blocks available for new file data (bitmaps or free lists).
  4. I-Node Table: An array of linear metadata records pre-allocated across contiguous tracks.
  5. Root Directory: The top-level directory node (often bound to i-node 2 in Unix filesystems).
  6. Data Blocks: The remainder of the volume dedicated to actual file content bytes and subdirectory tables.

4.3.2 Implementing Files: Allocation Strategies & Fragmentation

The central design challenge of a file system is mapping a linear stream of logical file bytes into physical storage blocks. Over time, file churn produces two distinct forms of fragmentation:

  • External Fragmentation: Free blocks become scattered in non-contiguous gaps. In contiguous allocation models, external fragmentation prevents new files from being written even when total free space is sufficient.
  • Internal File Fragmentation: In FAT and linked systems, a single file's cluster chain becomes scattered randomly across the volume. Reading the file sequentially requires repeated mechanical head seeks, dropping throughput significantly.

4.3.5 Log-Structured File Systems (LFS)

Traditional Unix and FAT filesystems distribute metadata and file data across random locations on disk. As disks grew much faster than seek times, random disk head seeks became the primary performance bottleneck. Log-Structured File Systems (LFS) fundamentally redesign storage by transforming the disk into a continuous sequential log.

Core Architecture & Operation

  • Sequential Write Buffer: All writes—including file data, directories, inodes, and indirect blocks—are buffered in main memory and written out sequentially in large contiguous segments.
  • Inode Map (imap): Because inodes move around constantly as files are updated, LFS maintains an inode map stored within the log that tracks the current physical location of every inode.
  • Checkpoint Region: Points to the latest root of the inode map and last segment summary, enabling rapid mounting and recovery upon reboot.
  • Segment Cleaner: A background daemon that reads partially dead segments, compacts live blocks, and writes them out as new clean segments to maintain continuous free space.

4.3.6 Journaling File Systems

System crashes mid-write often leave traditional filesystems in an inconsistent state, requiring lengthy full-volume integrity scans (such as fsck). Journaling File Systems (e.g., ext4, NTFS, XFS) solve this by introducing Write-Ahead Logging (WAL) to guarantee crash consistency.

Transaction Mechanics

  1. Intent (Journaling): Before modifying primary on-disk structures, the operating system writes a description of the planned changes (transaction intent) into a dedicated circular journal area.
  2. Commit Record: Once all metadata updates are written to the journal, a final commit record is appended, marking the transaction as atomic and complete.
  3. Checkpointing: Background threads copy the changes from the journal to their permanent locations on the main filesystem blocks.
  4. Recovery: Upon reboot after an abrupt power failure, the filesystem simply replays committed transactions from the journal, eliminating the need for slow multi-pass volume scans.

4.3.7 Flash Storage & Wear-Leveling Systems

Solid-state drives (SSDs) built on NAND flash memory replace mechanical platters with electronic memory cells. However, flash memory exhibits physical constraints that require specialized filesystem and controller layers:

  • Asymmetric Read/Write/Erase: Data can be read and programmed in small pages (e.g., 4KB), but can only be erased in large blocks (e.g., 2MB to 8MB). Erasing requires high voltage pulses that degrade physical oxide layers over time.
  • Write Amplification Factor (WAF): The ratio of data written to the flash media versus data written by the host operating system. High WAF reduces drive lifespan.
  • Flash Translation Layer (FTL): A firmware layer that translates logical block addresses (LBAs) from the file system to physical flash addresses, handling garbage collection and address remapping.
  • Wear-Leveling & TRIM: Algorithms that evenly distribute write cycles across all physical memory blocks to prevent premature cell burnout. The TRIM command allows operating systems to inform the SSD which blocks no longer contain valid data, optimizing background garbage collection.

4.3.8 Virtual File Systems (VFS)

Modern operating systems concurrently support multiple disparate storage formats (e.g., ext4, NTFS, FAT32, NFS, tmpfs). To prevent application software from needing format-specific system calls, operating systems implement the Virtual File System (VFS) abstraction layer.

VFS Object-Oriented Abstraction Model

The VFS defines a common software interface and four primary object types that encapsulate any underlying filesystem:

  • Superblock Object: Represents a specific mounted filesystem instance, storing global volume properties and mounting state.
  • Inode Object: Represents a specific individual file or directory, containing metadata (permissions, timestamps, size) and pointers to operation tables.
  • Dentry (Directory Entry) Object: Represents a single component of a path name, caching hierarchical directory lookups to accelerate path resolution.
  • File Object: Represents an open file instance associated with a specific process file descriptor, tracking current file offset and access mode.
